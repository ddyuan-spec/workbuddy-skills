# proto-spec（原型 spec 前置流程）

**把"长 PRD → 一次性生成 HTML"改成"先出 spec 文字 → 用户确认 → 再画 HTML"。** 这是从老袁《从长 PRD 到可交互 HTML：7 个可控阶段》提炼出的可复用流程，补我们 proto 系 skill「生成前结构化中间产物缺位」的短板——我们强在机器验收（smoke + 点击穿透），弱在生成前的 spec 锚点，本 skill 专补这一段。

> 本 skill 只产 spec（Markdown），**不画 HTML**。spec 确认后交接 proto-c / proto-admin / proto-design 实际生成。

## 触发（出现以下任一即先走本 skill）
- 用户给了一份长 PRD / 需求文档，要转原型
- 要新建一个多页面原型（≥3 页或含跳转）
- 改原型但不确定影响范围（单页还是全局）
- 用户说"先规划下 / 先出规范 / 先画导航地图"

## 核心思想：spec 驱动（唯一事实源 = Markdown）
HTML 是 spec 的执行结果，不是起点。先文字确认三件套，避免「画完才发现跳转漏了 / 风格漂移 / 改一处崩全局」。

---

## 强制门禁（生成前，BLOCKER 一票否决）

0. **SPEC-000 路由门禁**：凡要画 / 改原型，先判断——是「新建多页」还是「单页增量改」？新建必跑全量三件套；增量改必跑 SPEC-004 影响判定。未做判定禁止直接进 proto-c/proto-admin 开画。
1. **SPEC-001 三件套先出**：`NAV-MAP.md`（导航地图）+ `PUBLIC-SPEC.md`（公共规范）+ `PAGE-SPEC.md`（页面 spec）三份 md 不齐全，禁止进图形生成阶段。
2. **SPEC-002 设计规范必须用户确认**：公共规范（色板 / 设计 token / 类型规范 / 项目基线）**必须经用户逐条确认**，删掉「自动命中基线 / 用兜底风格」的默认行为。用户没回确认前，不得假定任何风格。每一次新项目 / 新模块都要重新问，不继承上一版的"默认"。
3. **SPEC-003 导航地图登记门禁**：任何页面跳转（`go('xxx')` / 点击进页）**必须先登记**到 NAV-MAP：源页 id → 目标页 id → 触发方式。未登记的跳转禁止写进原型；proto-c 冒烟 [B] 段会反向校验「原型里出现的 go() 目标必须都登记在 NAV-MAP」。
4. **SPEC-004 增量修改影响范围判定**：接到「改原型」需求先判定影响域——**单页**（只改某页内部，不动公共 token / 不改其他页跳转）还是**全局**（动 PUBLIC-SPEC / style.css / 公共组件 / 影响其他页）。单页改只重跑该页验收；全局改必须重跑全量八项验收 + 全量点击穿透。
5. **SPEC-005 八项验收基线先立**：在 PAGE-SPEC / ACCEPTANCE.md 里先写清八项验收口径（见下），画完对照打勾，禁止「画完凭感觉说差不多」。
6. **SPEC-006 参考图优先复刻（BLOCKER，有参考图时强制，衔接 proto-c/proto-admin 的 PROTO-REPLICA-001）**：凡要画/改的原型有真机/参考截图，在出 PAGE-SPEC 前必须先把「复刻基线」和「变更清单」写进 spec：①**复刻基线**——逐屏读全截图，在 PAGE-SPEC 顶部列出「截图原有字段清单 + 功能入口清单」；②**变更清单**——读需求/口述变更，列出本次相对截图要改的条目（新增/删除/修改字段、改/新增功能）；③ PAGE-SPEC 最终只描述两类内容：**A 类=截图原有字段/功能（在基线）**、**B 类=需求要求的新字段/功能（在变更清单）**，任何既不在基线也不在变更清单的字段禁止写进 spec（即臆造，需 `AskUserQuestion` 反问确认才加）。spec 确认后交接 proto-c/proto-admin 时一并交付这份「字段溯源表」，对方按 PROTO-REPLICA-001 落地复刻 + 复查。

## 标准流程

### Phase 0：确认生成目录 + 锁定 PRD 来源
- 确认输出目录（单文件 HTML 放哪 / 多文件项目结构）。
- 锁定 PRD 来源（用户给的文档路径 / 截图 / 口头需求），无 PRD 则先 `AskUserQuestion` 补全关键页面与流程（复用 proto-c 九步确认精神）。

### Phase 1：导航地图 `NAV-MAP.md`（SPEC-003）
登记所有页面与跳转关系。模板：

```markdown
# 导航地图（NAV-MAP）
项目：<项目名>  生成日期：<YYYY-MM-DD>

## 页面清单
| 页面 id | 页面名 | 类型 | 数据来源 |
|---|---|---|---|
| home | 首页 | 列表 | <PRD §x / 接口> |
| detail | 详情 | 独立页 | <截图 ref> |

## 跳转关系（每个 go() 必须登记）
| 源页 | 触发 | 目标页 id | 说明 |
|---|---|---|---|
| home | 点卡片 | detail | 进详情 |
| detail | 返回 | home | 返回首页 |

## 公共入口
- 底部 Tab：home / task / mine（固定 3 个，禁动态增减）
```

### Phase 2：公共规范 `PUBLIC-SPEC.md`（SPEC-002，必须用户确认）
先起草初稿 → **AskUserQuestion 让用户逐项确认** → 确认后才算定稿。模板：

```markdown
# 公共规范（PUBLIC-SPEC）—— 待确认
> ⚠️ 以下为初稿，必须经用户确认后才生效，禁止默认采用。

## 设计 token（骨架）
- 主色：<hex>  辅色：<hex>  危险色：<hex>
- 圆角：8px  间距基准：4px 栅格
- 字体：<system / PingFang / Microsoft YaHei>
- 状态色：成功/警告/错误 各 <hex>

## 类型规范
- 列表 item：左图右文 / 上图下文（二选一，禁混排）
- 空状态：图标 + 文案 + 操作按钮
- 加载：骨架屏 / spinner（二选一）

## 项目色板 / 视觉签名
- 本项目视觉签名元素：<如顶部色带 / 卡片描边 / 特定 icon 风格>
- 明确禁止：蓝紫渐变 / 通用卡片堆叠 / 系统默认阴影
```

确认后把「待确认」改为「已确认 @<user> <date>」。

### Phase 3：页面 spec `PAGE-SPEC.md`
逐页写清：布局、区块、状态、交互、示例数据、边界。模板：

```markdown
# 页面 spec —— <页面名>
页面 id：<id>  来源：<PRD §x / 截图 ref>

## 布局
- 顶部：标题栏（返回 + 标题）
- 中部：列表（卡片样式见 PUBLIC-SPEC 类型规范）
- 底部：Tab 栏

## 状态（≥3 态必须拆独立页，禁单页 Tab 切）
- 空态 / 有数据 / 加载中

## 交互
- 点卡片 → go('detail')（已登记 NAV-MAP）
- 下拉刷新 → 重新拉列表

## 示例数据
- 列表 3 条：<字段值>

## 边界 / 异常
- 网络失败 → Toast「加载失败，点击重试」
```

### Phase 4：八项验收清单 `ACCEPTANCE.md`（SPEC-005）
画完逐条打勾，作为交付前验收基线：

| # | 验收项 | 口径 | 结果 |
|---|---|---|---|
| 1 | **布局对** | 像素级对参考截图 / PRD 描述，无错位 | ☐ |
| 2 | **视觉签名一致** | 色板 / token 命中 PUBLIC-SPEC，无漂移 | ☐ |
| 3 | **避免 AI 默认风格** | 无蓝紫渐变 / 通用卡片堆叠 / 系统阴影 | ☐ |
| 4 | **文案基调一致** | 全站统一（聊天体 / 品牌调性），无混搭 | ☐ |
| 5 | **跳转通** | NAV-MAP 全覆盖，无死链 / 空白跳 | ☐ |
| 6 | **状态齐** | 三态拆独立页，无单页 Tab 假切 | ☐ |
| 7 | **交互真** | 点击穿透状态真的变（数值+N / 页切换） | ☐ |
| 8 | **无悬空** | 引用完整（id / 函数 / 样式类都有定义） | ☐ |

### Phase 5：公共资产抽离（SPEC-002 的延伸）
- 设计 token 与公共样式集中到 `style.css`（或原型内 `<style>` 顶部 token 区），禁每页重复硬编码。
- 示例数据集中到 `mock-data.js`（或统一 data 区块），禁散落各页。
- 这样增量改（SPEC-004 全局）只动一处。

### Phase 6：交接
- 带交互 C 端 → **proto-c**（把三件套 md 路径传给它，它按 spec 画 + 跑冒烟 / 点击穿透）
- 后台 → **proto-admin**
- 平铺 / 墨刀 / 可复制源码 → **proto-design**
- 交接时明确：本次是「全量新建」还是「<page> 单页增量改」（决定对方跑全量还是单页验收）

---

## 增量影响判定表（SPEC-004）

| 改动类型 | 判定 | 验收范围 |
|---|---|---|
| 改某页内部文案 / 布局 | 单页 | 该页八项 + 该页点击穿透 |
| 改某页跳转目标 | 单页 + NAV-MAP | 该页 + NAV-MAP 一致性 |
| 改 PUBLIC-SPEC token / 色板 | **全局** | 全量八项 + 全量点击穿透 |
| 改公共组件 / style.css | **全局** | 全量八项 + 全量点击穿透 |
| 新增页面 | 全局 + NAV-MAP | 全量八项 + 全量点击穿透（新页补 Step） |

## 关联
- `proto-c` / `proto-admin` / `proto-design`：spec 确认后的实际生成端，本 skill 是它们的前置。
- `requirement-workflow`：需求 intake 壳，spec 来源之上游。
- `prd-suite` / `delivery-suite`：原型定稿后的结构排查与推送。
- 机器验收（smoke / 点击穿透）仍由 proto-c / proto-admin 负责——本 skill 只补「生成前的 spec 锚点」，不重复造验收轮子。
