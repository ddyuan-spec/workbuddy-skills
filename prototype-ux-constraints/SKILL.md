# 原型UX约束规范（前端交互）

## 触发条件

- 生成/修改任何含前端交互的原型（H5 / App / 小程序 / 后台管理端）时必须调用。
- 特别适用场景：商品购买级别限制、权限拦截、会员等级限制、资格校验等前端反馈。

## 核心约束

### 1. 禁止多余说明文案

- ❌ 禁止在原型页面内写「前端拦截说明」「规则说明」「* 注意」「演示：当前...」等解释性卡片或段落。
- ❌ 禁止在规格/选项/字段下方写「后台设置了 xxx」「该字段含义是 xxx」「仅辅助提示」等备注。
- ❌ 禁止在页面角落、右侧、底部加演示说明、状态注释、图例。
- ✅ 所有业务规则、异常说明、字段映射应放入 PRD；原型只保留真实界面元素。

### 2. 禁止前端小字限制标签（重要）

- ❌ 禁止在规格按钮、选项标签、商品名称、价格旁加 tiny 小字限制提示，例如：
  - `🔒限高级`、`限高级+`、`限VIP`、`仅限会员`、`会员专享`、`仅对高级会员可见` 等。
  - 任何 `font-size ≤ 10px` 且含「限」「仅限」「专享」「会员可见」「🔒」等字样的标签/角标。
- ✅ 购买级别限制只通过**后台配置字段**（如「购买级别(≥)」下拉）和**加购/购买时的全局 Toast** 表达，不在前端界面上贴小字提示。
- ✅ 若需要让用户感知级别门槛，通过 PRD 描述，不在原型里加视觉标签。

### 3. 小字限制文案扫描与确认 Loop（强制）

生成/修改原型后，必须执行以下扫描 loop，直到无命中项：

1. **正则扫描**：在 HTML/CSS/JS 中搜索以下模式：
   - 文本内容含 `限`、`仅限`、`专享`、`会员可见`、`🔒` 等关键字。
   - 类名如 `.lock`、`.limit`、`.vip-tag`、`.member-only` 等。
   - `font-size:9px`、`font-size:10px` 等 tiny 样式附近有限制含义文案。
2. **用户确认**：每发现一处，向用户展示具体代码片段，询问「这段小字限制标签是否需要保留？」
   - 用户回答**不要** → 立即删除，并记录该文案模式到记忆。
   - 用户回答**保留** → 保留，并记录为例外。
3. **记忆生效**：用户已确认删除的小字模式，**后续同类型无需再问，直接删除**。
   - 记忆写入位置：`C:\Users\13364\WorkBuddy\绿韵家\.workbuddy\memory\MEMORY.md` 与 `~/.workbuddy/MEMORY.md`（跨项目）。
   - 记忆格式示例：「前端原型中规格/选项旁的“🔒限高级”“限高级+”“限VIP”等 tiny 限制小字，用户已确认不需要，后续直接删除。」
4. **重新扫描**：删除后继续 loop，直到扫描无命中。

### 4. 禁止臆测新样式/组件

- ❌ 禁止为了一次提示单独设计气泡 `.bubble` `.fe-bubble` `.tip` `.hint-pop`、小红标说明、新模态弹窗样式。
- ✅ 复用项目现有全局组件：全局 Toast / 全局弹窗 / 页面已有提示样式。
- ✅ 提示文案极简，只保留必要一句，例如「该商品仅限高级会员及以上才能购买」。

### 5. 拦截提示时机（购买级别 / 权限类场景）

- ❌ 用户**选中规格 / 切换选项 / 点击单选**时**不触发**任何拦截提示。
- ✅ 只有用户点击**加入购物车**、**立即购买**或实际提交动作时才触发提示。
- ✅ 提示后保持规格可选中状态，**不做置灰、不阻断继续切换规格**。

### 6. 交互即交互，不堆说明

- 原型里每个可点击元素必须有对应反馈。
- 不要为了让评审者看懂而加文字说明；看不懂的走 PRD 和面对面沟通。

### 7. 先盘点既有原型，能复用就复用（禁止从零重造）

- ✅ 画新需求原型前，**先盘点项目内既有同模块原型**（如 `优惠券体系/*.html`、其他需求文件夹的 `*.html`），列出可复用的页面 / 组件 / 样式变量。
- ✅ 能复用的页面直接**复制改造**（改成本期范围、删掉不做的分支），复用既有类名、Toast / 弹窗实现，保持跨原型视觉一致。
- ❌ 禁止对已经存在的交互页面从零重写；只在既有原型缺页时新建。

### 8. 所有原型（含 C 端）必须确认样式基线，最开始即确认

- ✅ **画任何原型前（后台 / 管理端 / App / 小程序 / H5），最开始就必须先确认视觉样式基线**，禁止默默复用既有原型样式就开干。
- ✅ **后台 / 管理端**（平台端后台、商家端后台）：优先定位项目内既有后台参考页（如 `优惠券体系/live-admin.html`）。
- ✅ **C 端（App / 小程序 / H5）**：优先盘点 §7 既有同模块 C 端原型（如 `优惠券体系/live-client.html`）的视觉风格作为默认基线；**但即便有可复用原型，也必须显式向用户确认"是否以该基线为准"**（AskUserQuestion 或文字），得到确认或新稿前不产出。
- 🔴 **C 端强制首步（最高优先级）**：动手画任何 App / 小程序 / H5 界面**之前**，必须先用 `AskUserQuestion` 向用户确认「是否有 C 端设计稿 / 参考图？」，选项 = `有稿，我发你` / `沿用既有同模块基线（如 live-client.html）` / `暂无，先通用风格`。**未得到确认前，禁止产出任何 C 端界面**（哪怕只是先搭一页占位也不行）。
- ❌ 禁止凭空臆测布局 / 表格 / 表单 / 弹窗样式。
- ⚠️ **若用户手头有新设计稿 / 参考图，一律以用户稿为准**，按图重构样式，不沿用既有原型风格。
- ⚠️ **若全盘找不到任何参考页 / 基线，必须主动找用户要样式参考**（用 AskUserQuestion 或文字提问），拿到前不产出原型。此动作已固化为强制前置步骤。

### 9. 逐页 / 逐弹窗样式参考确认（强制 Loop）

画后台原型时（C 端若用户要求逐页 / 弹窗确认样式基线也走此 Loop），**不能只找一个全局参考页就全盘套用**。必须按以下流程逐一确认：

1. **列出全部页面 + 弹窗/抽屉清单**：先列出原型包含的所有页面（侧栏页）和所有弹窗/抽屉/详情页，编号命名。
2. **逐个 AskUserQuestion 确认样式来源**：对每一项问用户：
   - 「你有这个页面的样式参考截图/设计稿吗？」
   - 选项：`有参考，我给` / `沿用已有参考的同套风格` / `暂无，先画通用风格`
3. **记录样式参考矩阵**：汇总成表（名称 × 样式来源决策），存入记忆。
4. **缺参考的不画**：用户说「有参考，我给」但还没给的项，**等收到截图后再画该项**；其他项可先行。
5. **样式一致性**：多项选「沿用同套风格」的，共享同一套 CSS 变量与组件类名。
6. **修正即循环**：若用户在审查中发现某项实际样式与参考不符（如「不是抽屉是详情页」「不是弹窗是内嵌表单」「不是弹窗是独立编辑页」），立即修正并重新 loop 自检。

### 9.1 参考截图「逐字文案」核对 Loop（强制）

当用户提供真实后台 / 设计稿截图作为参考时，原型内**所有可见文案**必须与截图逐字比对，**禁止凭记忆、猜测或套用旧原型文案**。必须按以下流程 loop，直到全部命中且一致：

1. **列基线**：先把截图里**所有可见文字逐行抄出**（侧栏分组+菜单项、表头、按钮、筛选标签、面包屑、状态 Tag），存为核对基线清单。
2. **侧边栏菜单**：每个分组标题、每个菜单项（含二级子分组、含「-」连接符如「泰小虎直播 - APP直播」）与截图完全一致；折叠/展开态与截图一致。
3. **表头**：列表/表格每一列标题文字、顺序与截图一致。
4. **按钮 / 链接文案**：新建、搜索、重置、操作列每一项（查看/编辑/下架/删除/撤回/增加发行量…）与截图一致。
5. **筛选器标签与占位符**：每个 input placeholder、每个 select 默认项文字与截图一致。
6. **面包屑 / 页面标题**：与截图路由文案一致。
7. **状态 Tag 文字**：启用/下架/未开始/进行中/已结束/已删除等枚举值，与截图状态列完全一致（**截图有则必须有，截图无则不得臆造**）。
8. **开发期临时标记须删除**：截图中的 **NEW / HOT / BETA / v1.2** 等开发阶段或版本迭代产生的**临时角标/徽章/提示标签**，在原型中**一律不复制**（除非用户明确要求保留）。这些是上线后就会消失的运营标记，不是产品功能的一部分。典型：侧栏菜单旁的 `NEW` 紫色角标、列表标签类型列的 `NEW` 徽章。

⚠️ **真实教训**：用户给真实后台截图要求「一比一复刻侧边栏」，初版凭旧原型记忆写成「商品管理/行动管理/数据概览/营销管理…」，与截图实际「营销应用（营销管理/满减满赠/秒杀/拼团/积分商城/储值/泰小虎直播-APP直播）…」完全不符。→ 凡有参考图，**先列出截图全部文字作为基线再写原型**，写完逐条打勾，杜绝凭记忆编造。
⚠️ **真实教训**：标签管理页面截图中「直播标签」类型旁和侧栏「直播观看记录」旁均带有紫色 `NEW` 临时角标（上线后即消失的运营标记），初版原型错误复制了这些角标——**开发期临时标记（NEW/HOT/BETA）不是产品功能，原型中一律不复制，除非用户明确要求保留**。

### 10. 后台（平台端/商家端）增/改/查一律跳转独立页，禁用 Modal 弹窗

- ✅ 后台管理端（平台端后台、商家端后台）的所有「新增」「编辑」「详情」操作，**一律跳转独立页面（独立 view / 路由页）**，**不使用 Modal 弹窗**（`.modal-overlay` / `.modal`）。
- ❌ 禁止用 `openXxx()` + `modal-overlay.classList.add('show')` 这种弹窗模式实现后台新增/编辑/详情。
- ✅ 独立页结构：`phead`（返回按钮 + 动态标题 h2）+ `form-section`（表单主体）+ `form-actions`（取消/返回 + 保存/提交）。
- ✅ 列表页「新建」按钮 `onclick="go('xxxNew')"`；列表「编辑」链接 `onclick="editXxx(id)"` → `go('xxxEdit')` 后 `fillXxx(id)` 回填；保存后 `go('list')` 回列表；`go()` 的 view map 必须登记这些独立页。
- ✅ 详情页也是独立 view（如 `viewCouponDetail`），含「返回列表」+ 业务操作按钮（如「下架」）。
- ✅ 编辑回填：进入编辑页时从数据重建表单（含从选项池移动已选项时，**离开/重置表单须恢复选项池**，避免多次编辑后选项池被掏空的交互 bug）。
- ⚠️ 此规则优先级高于「复用既有弹窗式后台原型」：若既有后台原型用 modal 实现增改，**改造时改为独立页**。
- ⚠️ 用户在审查中说「这个弹窗应是独立编辑页/详情页」时，立即按此规则重构（实例：某项目曾把券详情从抽屉改为独立页、把新增券/发券活动/领券活动的 modal 弹窗全部改为跳转独立页）。

### 禁止"写死 / 不可编辑"说明文字（强制）

- ❌ 禁止在原型页面内出现「写死」「不可编辑」「固定值」「本期不可配置」「本期仅支持」「无法修改」等解释性文字或徽标（如 `.locknote`「⚠ 写死：直播时长」「⚠ 固定：30 分钟」这类黄色提示块）。
- ✅ **不可编辑直接用 `readonly` / `disabled` / 置灰样式表达**，不附加任何文字说明。评审者/开发看到置灰或只读字段即知不可编辑，无需语句解释。
- ✅ 列表里某字段当前是固定值（如触发源默认直播时长），直接显示该值即可；不要画蛇添足加"写死"标记。
- ⚠️ **除非用户在某次需求里明确指示"此处要加说明文字"**，否则一律不写。此规则优先级高于"为评审者解释不可编辑"的冲动。
- 违反本规则的文字属于多余描述，必须删除（见交付前 Loop 自检项）。

### 11. 重绘 / 套模板导致字段缺失必须 AskUserQuestion 确认（禁止静默掉需求）

- ❌ **禁止**在重绘页面、套用新模板、或与既有字段/列结构冲突时，**静默删除**用户此前已确认存在的字段、列、筛选器、交互（即"掉需求"）。典型场景：把列表套进新表格模板后某列不见了、把表单重绘后某输入项被模板结构吞掉、改名后关联字段丢失。
- ✅ 当新结构（模板 / 重绘）与既有字段冲突、或你判断某字段"应该去掉"时，**必须主动用 `AskUserQuestion` 向用户确认**，明确列出"以下字段将在本次改动中不再出现：X / Y / Z，是否确认删除？"——**得到用户明确确认后才能删**，否则保留。
- ✅ 若用户确认删除，在交付物 / 记忆中记录"X 字段经用户确认于 YYYY-MM-DD 移除"，便于回溯。
- ⚠️ **真实案例**：优惠券管理列表套新模板后，"店铺"筛选与"店铺"列被模板结构吞掉（用户明确说"之前在活动范围里头有个店铺选择这个字段没了"）—— 这类"掉需求"本应在重绘时立即 AskUserQuestion 确认，而非静默丢失。

## 12. 自动化冒烟测试（强制，替代纯人工 Loop —— 交付前必跑）

人工肉眼 Loop 不可靠：曾两次漏掉"独立页写在 `</main>` 之外 → 点击跳转后整页空白"的致命 bug（用户侧表现为"发券/领券的编辑和新增是空白页"，loop 的"交互完整性/样式正确性"逐条勾选却全过）。**改为用 jsdom 真实执行原型 JS 的自动化冒烟测试作为硬性门禁**：

- 检查器：`references/proto_smoke.js`（已随本 skill 提供，单文件零依赖，需 jsdom；缺失时自动临时安装）。**后台（平台端/商家端）原型用此脚本。**
- 运行（在原型所在目录）：
  ```
  NODE_PATH="<jsdom 所在 node_modules>" <managed-node> references/proto_smoke.js <原型.html>
  ```
  例：
  ```
  NODE_PATH="C:\Users\13364\.workbuddy\binaries\node\workspace/node_modules" "C:\Users\13364\.workbuddy\binaries\node\versions\22.22.2\node.exe" references/proto_smoke.js 平台端后台原型.html
  ```
- **C 端（App / 小程序 / H5）原型用 `references/proto_smoke_client.js`**（结构适配 `.phone` 外壳 + `.page` 容器切换，无 `<main>`/view* 独立页）。检查项同源：**[A]** 页面归属 `.phone`、**[B]** `go()` 可达且非空、**[C]** 真实点击捕获 JS 错误、**[D]** onclick 函数定义、**[E]** JS 运行期错误、**[F]** 表单选项去重。
  例：
  ```
  NODE_PATH="C:\Users\13364\.workbuddy\binaries\node\workspace/node_modules" "C:\Users\13364\.workbuddy\binaries\node\versions\22.22.2\node.exe" references/proto_smoke_client.js App端原型.html
  ```
- 检查项（任一项失败 → 禁止交付，先修复）：
  1. **[A] 视图容器归属 `<main>`**：所有 `view*` 独立页 / 弹窗必须在 `<main>` 内，写在 `</main>` 之外直接判失败（空白页根因）。
  2. **[B] `go()` 可达性 + 空白校验**：每个 `go('X')` 目标视图必须存在、跳转后可见、且有内容（非空白页）。
  3. **[C] 真实点击每个可交互元素**：捕获 JS 运行期错误（如 `undefined.trim()`、未定义变量）。
  4. **[D] onclick 函数未定义扫描**：所有 `onclick` 引用的函数必须已定义。
  5. **[E] JS 运行期错误汇总**：`virtualConsole` 捕获的所有 jsdomError / console.error（已对 `confirm/toast/$` 等浏览器环境项注入 shim，仅报真实 bug）。
- 退出码：0=全部通过可交付；1=有失败项；2=参数错误。**任何失败项都必须修复后才能交付原型。**
- ⚠️ 本测试已用正/反例验证：健康文件全绿；把发券/领券独立页移到 `</main>` 外会立即报 `#viewSendEdit/#viewClaimEdit 写在 </main> 之外 → 跳转后空白页`。

## 13. 平铺交互 / 评审板格式规范（强制）

当需求产出「平铺交互 HTML / 页面评审板」时（即把所有原型页面截图铺在同一页供评审查看），**必须遵守以下卡片格式规则**：

### 卡片内容三件套（仅此三项，多一不可）

每张评审卡片的可见内容**严格限定为**：

1. **截图**（`<img>`）— 原型页面的实际截图
2. **页面名称** — 简短标题（如「C2 我的优惠券」「P1 券列表」）
3. **「查看详情」按钮** — 点击后弹 Modal 展示完整 PRD 文字说明

### ❌ 禁止出现在卡片上的内容

以下内容**禁止直接展示在卡片上**（包括但不限于）：

| 禁止项 | 说明 |
|---|---|
| 🚫 **文字说明/摘要段落** | 不在卡片内放任何描述性文字、功能说明、范围说明 |
| 🚫 **页面列表/导航清单** | 不列出「H首页 / M商城 / U我的 / C2…」这类页面索引 |
| 🚫 **PRD 字段表/逻辑规则** | 这些内容仅在 Modal 详情中展示 |
| 🚫 **侧栏/分组说明文字块** | 截图旁边不附大段解释性文本 |
| 🚫 **原型侧栏导航文字** | 如果原型自带 `.side` 侧栏，截图中已包含即可，不在卡片外再复制一份 |

### ✅ 正确的卡片结构

```
┌──────────────────────┐
│   [页面截图]          │  ← 唯一的视觉主体
│                      │
├──────────────────────┤
│ C2 我的优惠券         │  ← 名称（一行）
│           [查看详情]  │  ← 按钮（右对齐）
└──────────────────────┘
```

### 布局分区

- **两大区**：C端（用户侧） / 后台（管理侧），用视觉分隔区分
- 每区内卡片横排（flex-wrap），等宽等高
- 顶部仅保留：标题 + 总数 + 搜索框（不超过一行）

### ⚠️ 违规案例

用户明确反馈过的问题（2026-07-30 评审）：
- ❌ 卡片下方出现大段文字：「本期范围（App 端新增）：获券弹窗…/我的优惠券（三态）/确认订单选券与下单核销。⚠️ 获券触达可含多张…」+ 页面清单列表 — **全部删除，移入 Modal**
- ❌ 卡片内嵌原型自带的侧栏导航文字（`.side .desc` 内容）— **不应作为卡片额外信息展示**

## 交付前自检 Loop（生成 / 修改原型后必须 loop 执行，直到全部通过）

> ⚠️ **本 Loop 必须与 §12 自动化冒烟测试共同执行**：先跑 `proto_smoke.js` 且零失败、零 JS 错误，再做下列人工逐项核对。自动化测试不通过一律禁止交付。人工 Loop 负责自动化测不到的视觉/文案层面（样式错乱、冗余文字、小字限制标签、复用一致性），自动化测试负责 DOM 结构 / 交互可达性 / JS 错误层面。

每轮检查后修正问题并重新检查；以下任一项不通过则继续 loop，禁止带着问题交付：

- [ ] **交互完整性**：页面内每一个按钮 / 链接 / 标签切换 / 表单提交 / 状态变更都有对应反馈（点击、跳转、弹窗、Toast、显隐切换），无「死」交互、无掉落的交互分支、无只画不响应的元素。
- [ ] **样式正确性**：无布局错乱、无未定义 / 裸样式类、无溢出 / 重叠 / 文字截断、无响应式破版、无错别字 / 残缺文案。
- [ ] **无冗余说明文字**：页面内无「说明」「规则」「注意」「演示」「备注」「图例」「前端拦截」类文字块（业务规则只在 PRD）。
- [ ] **无"写死/不可编辑"说明文字**：grep `写死`、`不可编辑`、`固定值`、`本期不可`、`本期仅支持`、`无法修改`、`locknote` 应**零命中**；不可编辑仅用 `readonly`/`disabled`/置灰样式表达，不附任何文字说明（除非该次需求用户明确要求加）。
- [ ] **表单选项无重复/错漏**：所有 `<select>` 下拉、`<input type=radio>` / `checkbox` 分组的选项文本**不得重复**（如两个 option 都是「满减券」）、不得有占位/空值混入正式选项（如 value 为空但 label 是真实选项名）、不得遗漏需求明确的选项（如截图明确 4 种券类型但只写了 3 种）。检查方法：逐个 `<select>` 列出所有 `<option>` 文本去重比对；逐个 radio/checkbox group 核对 label 唯一性。⚠️ **真实案例**：新增券页优惠券类型下拉出现两次「满减券」且缺「满折券」—— 冒烟测试的 JS 层面不报错（语法合法），必须靠本项人工核对拦截。
- [ ] **无小字限制标签**：页面内无 `🔒限高级`、`限高级+`、`限VIP`、`仅限会员` 等 tiny 限制小字；已按 §3 扫描并处理。
- [ ] 无新增气泡 / 弹窗样式类（搜索 `.bubble` `.fe-bubble` `.tip` `.notice` 等）。
- [ ] 选中规格 / 选项的函数内无提示调用（`toast` / `alert` / `showBubble` 等）。
- [ ] 仅「加入购物车」「立即购买」或提交动作函数内有提示调用。
- [ ] 提示使用现有全局 Toast / 弹窗，而非新建 DOM 组件。
- [ ] **后台增改查无 Modal**：后台平台端/商家端的所有新增/编辑/详情均为独立页（grep `modal-overlay` 应零命中），无弹窗式增改。
- [ ] **DOM 结构校验（视图容器归属）**：所有 `viewXxx` 独立页 / 弹窗必须在布局容器（`<main>` / 内容区）**内部**，禁止写在 `</main>` 或内容区闭合标签之外（否则跳转后显示空白页）。检查方法：确认 `</main>` 或等效内容闭合标签的位置，所有视图 div 必须在其之前。⚠️ **真实案例**：某次把 3 个独立页写在 `</main>` 之后，导致点击"新增"跳转后完全空白 —— loop 的"交互完整性"和"样式正确性"均未捕获此 bug，必须专项检查。
- [ ] **复用核对**：后台原型已基于参考页（或已找用户要到参考）；前端原型已复用既有同模块原型的可复用部分，无重复造轮子。
- [ ] **掉需求核对（重绘 / 套模板后必查）**：对比本次改动前的版本（或需求确认稿），列出原有字段 / 列 / 筛选器 / 交互清单，逐一核对是否全部保留；**发现任一字段在本次重绘 / 套模板中消失（被模板结构吞掉、改名导致关联丢失等），必须回溯确认是用户明确同意删除的，否则视为"静默掉需求"→ 立即补回并触发 §11 的 AskUserQuestion 确认流程**。⚠️ 真实案例：优惠券列表套新模板后"店铺"筛选与"店铺"列被吞掉，用户事后指出"字段没了"—— 此类必须在重绘前/中主动问用户，而非交付后被挑出。
- [ ] **平铺评审板格式合规（如有产出）**：若本需求产出「平铺交互 HTML / 评审板」，每张卡片仅含「截图 + 名称 + 查看详情按钮」三项，**不含任何文字说明/摘要/页面清单/PRD内容**（详见 §13）。违规典型：卡片下方出现大段说明文字或页面导航列表 → 删除，移入 Modal 详情。
- [ ] **参考截图文案逐字核对（有参考图时必查）**：若本次需求用户提供真实截图 / 设计稿，已将截图内所有可见文字（侧栏分组+菜单项 / 表头 / 按钮 / 筛选标签 / 面包屑 / 状态 Tag）逐行列出作为基线，原型逐项打勾一致；**截图有则必须有、截图无则不得臆造**（详见 §9.1）。违规典型：凭旧原型记忆写侧栏，漏掉截图真实分组与菜单项（如把「营销应用」写成「商品管理」）。
- [ ] **开发期临时标记已清除（有参考图时必查）**：截图中的 NEW / HOT / BETA 等开发阶段角标/徽章已从原型中删除，未错误复制进原型（详见 §9.1 第 8 条）。除非用户明确要求保留。
