# 需求拆透（requirement-analysis）

> **为什么存在**：产品经理最容易出问题的地方，不是不会写 PRD、不会画原型，而是**需求一开始没拆透**，然后"在评审会上被一堆问题打回来"——状态从哪来、重复提交怎么办、按钮谁能看到、失败有没有兜底、历史数据怎么处理。
> 本 skill 把"需求拆透"固化成固定 6 步。拿到需求后先跑这套，再进 PRD / 原型 / 评审。
> **这是默认前置动作**：见 requirement-confirm-gate 与 requirement-workflow 的强制门禁。

## 何时触发（强制前置）
- 用户给了一段新需求 / 反馈 / 评审意见，要据此产出或修订 PRD / 原型；
- 任何"写/改/审 PRD、画/改原型、评审、推线上"任务的**开头**；
- 例外（轻量模式）：纯排版 / 纯文案润色 / 已知明确的单点字段修改，可跳过分析只走 confirm-gate 反问；其余一律先拆透。

## 执行步骤（固定 6 步，顺序不可省）

### 第 1 步：还原真实问题
别急着讨论功能，先判断需求描述是「问题」还是「方案」。
- 业务方表面提出的需求是什么？
- 背后**真正想解决的问题**是什么？
- 当前方案是否只是其中一种解法？
- 还有没有其他可能的解决路径？
> ⚠️ 若真实问题没找到，后面 PRD 写得再完整也只是把错误方案包装得更正式。**本步未过，不许进 PRD。**

### 第 2 步：识别用户角色
输出角色表（每个角色一行）：
| 角色名称 | 角色目标 | 使用频率 | 关注信息 | 操作权限 | 与其他角色关系 |
- 区分"使用的人 / 管理的人 / 决策的人 / 受影响的人"，避免一个功能想满足所有人最后谁都不顺。

### 第 3 步：拆具体场景
每个场景包含：场景名称 / 触发时机 / 用户当前状态 / 用户想完成什么 / 系统应提供什么帮助 / 优先级（高-中-低）。
- 警惕"用户需要这个功能"这种笼统描述，必须落到具体场景。
- 场景越清楚，后面的页面 / 流程 / 状态 / 规则才越稳。

### 第 4 步：梳理业务流程（泳道思路）
按"用户 / 系统 / 后台 / 管理者"视角拆。每一步标注：① 由谁触发 ② 系统需要判断什么 ③ 输入与输出 ④ 涉及的数据状态变化。
- 是**业务流程**不是页面流程；先想业务怎么发生，再想页面怎么承载。

### 第 5 步：异常与边界扫描（★ 对齐 PRD 异常红线，重点）
固定做一次 8 类异常扫描，用表格输出：**异常场景 / 触发条件 / 影响 / 产品处理建议**。
| 类别 | 典型问题 |
|---|---|
| 1. 用户操作异常 | 误触、中途退出、重复提交 |
| 2. 系统状态异常 | 状态已变、状态机死锁 |
| 3. 数据异常 | 数据为空、格式错、量级溢出 |
| 4. 权限异常 | 无权限看到/操作、越权 |
| 5. 网络/接口异常 | 接口失败、超时、重试 |
| 6. 并发/重复操作 | 双端同时操作、幂等 |
| 7. 历史数据兼容 | 旧数据不兼容新规则 |
| 8. 运营后台处理异常 | 后台误操作、批量异常 |
> **强对齐 PRD §四**：每个功能点的"逐步操作逻辑"必须含**异常分支 + 校验提示文案**。扫描出的异常项，若有不确定处理方案：
> - 文档内以「⚠️ 待确认 @干系人」占位（禁止臆测值）；
> - 或用 AskUserQuestion 反问具体处理规则。

### 第 6 步：模拟评审（三方质疑）
让 AI 分别扮演**资深研发 / 测试负责人 / 业务负责人**，各提 ≥10 个尖锐问题（要具体、指出缺失信息），最后总结**当前最大 5 个风险**。
- 研发关注：数据结构、接口返回、状态流转、老系统兼容；
- 测试关注：异常怎么测、边界怎么测、失败场景、回归影响；
- 业务关注：解决什么问题、上线怎么看效果、是否增加一线负担、有无运营抓手。

## 产出结构（跑完 6 步必须给这 5+1 样）
1. **真实问题**：需求到底解决什么（不再只停在业务原话）。
2. **角色清单**：谁使用 / 管理 / 决策 / 受影响。
3. **场景拆解**：用户在什么情况下需要这个能力、优先级。
4. **业务流程**：从触发到结束每步怎么走（泳道）。
5. **风险问题**：哪些没想清、易被研发/测试挑战。
6. **结论**：当前是否清晰 / 最大风险 / 需补充信息 / **是否建议进入 PRD 阶段**。

## 交接协议（拆透 → 下一步）
- 结论为"建议进 PRD" → 把上述 6 项作为 PRD 输入，路由 `prd-suite` 写 PRD；异常项用「⚠️ 待确认」占位。
- 结论为"未想清 / 风险大" → 先就风险项用 AskUserQuestion 反问，补完再判断。
- 若要画原型 → 拆透结论同步给 `proto-spec` 作为三件套（NAV-MAP/PUBLIC-SPEC/PAGE-SPEC）的事实源。
- 路由壳：`requirement-workflow` 收到需求后**先调本 skill 拆透**，再 intake / 路由。

## 可直接复制的完整 Prompt
```
你现在是一位拥有 10 年经验的资深产品负责人，擅长复杂业务需求分析。
我会给你一个需求，请你不要急着写 PRD，也不要直接给方案。请先帮我完成需求分析，按以下结构输出：
一、真实问题分析：1.业务方表面提出的需求是什么？2.背后真正想解决的问题是什么？3.当前方案是否只是其中一种解法？4.还有没有其他可能的解决路径？
二、用户角色分析：1.涉及哪些用户角色？2.每个角色的目标？3.关注什么信息？4.有哪些操作权限？
三、使用场景拆解：1.用户会在什么情况下使用？2.高频场景？3.低频但重要的场景？4.哪些应优先支持？
四、业务流程梳理：1.按步骤输出完整业务流程。2.每一步由谁触发？3.系统需要判断什么？4.每一步输入输出？5.涉及哪些状态变化？
五、异常和边界场景：从用户操作、系统状态、数据、权限、网络、并发、历史数据、后台处理等角度，列出可能遗漏的异常场景（异常场景/触发条件/影响/产品处理建议）。
六、模拟需求评审：分别扮演资深研发、测试负责人、业务负责人，各提≥10个尖锐问题，最后总结最大5个风险。
七、最终输出：1.需求是否清晰？2.最大风险？3.需补充信息？4.是否建议进入 PRD 阶段？
需求内容如下：【粘贴你的需求】
```

## 需求分析 Checklist（不想写 Prompt 时用）
收到需求后先问自己 10 个问题：① 这是问题还是方案？② 真实目标是什么？③ 涉及哪些角色？④ 最高频场景是什么？⑤ 业务流程谁触发、状态怎么变？⑥ 用户操作异常怎么办？⑦ 数据为空/出错怎么办？⑧ 没权限的人看到会怎样？⑨ 历史数据兼容吗？⑩ 研发/测试/业务会挑战什么？

## 红线（违反即算失误）
- ❌ 拿到需求直接写 PRD / 画原型，跳过拆透。
- ❌ 第 1 步真问题没找到就往下做。
- ❌ 第 5 步异常扫描偷懒——这是评审会翻车重灾区，必须出 8 类表格。
- ❌ 异常项填臆测处理方案；必须「⚠️ 待确认占位 + 反问」。

## 与其他 skill 的关系
- `requirement-confirm-gate`：最前置门禁，确认理解。**确认后、产出前必须先调本 skill 拆透**。
- `requirement-workflow`：intake 壳，收到需求**先路由本 skill**，再分发 prd-suite / proto-*。
- `prd-suite`：拆透结论作为 PRD 输入；异常项承接「⚠️ 待确认」。
- `proto-spec`：拆透结论作为三件套事实源（需求先拆透，原型才不堆页面）。
- `pm-review-board`：拆透第 6 步模拟评审可复用其多角色评审视角。
