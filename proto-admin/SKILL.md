# proto-admin（后台原型）

**规则本体在 `rules.json`，本文件只是调度壳。动手画/改任何后台原型前必须先读 `rules.json`。**

> 通用 UX 红线（禁冗余文字 / 禁 NEW 角标 / 视图在容器内 / 复用不掉需求等）与 `proto-c` 同源，修改须同步两端（见 rules.json `common_source_note`）。本 skill 只额外持有后台专属门禁。

## 原型修改总纲（PROTO-MOD-001，所有增量修改通用，BLOCKER）

> 上位原则：无论有无参考截图都生效，覆盖 `PROTO-REPLICA-001`（有参考图）/ `PROTO-FEAT-001`（禁臆测）。改原型先默念。

接到「改原型 / 加个 XX / 优化一下」类需求时遵循「复制为主、只增不改」：

1. **以复制为基底**：默认在现有原型文件上做最小改动，不重写、不重画、不换实现方式；新建独立演示也从现有原型复制基底，不凭记忆新起。
2. **只动变更单内的点**：需求明确指出的新增/删除/修改点才动，产出变更清单逐项核对。
3. **未列入清单一律保留**：现有字段、选项、文案、结构、样式、配色、间距，只要没在变更清单里就原样保留、像素级不动。
4. **禁止顺手动刀**：严禁借改原型顺手做优化/清理/重做/统一风格/改文案/换组件/调间距等一切变更单外动作，即便「看起来更好」也算违规。
5. **改完必做 diff 自检**：对比改动前后，确认只有变更单内的点变了、其余与改动前完全一致；交付前在回复给出改动范围小结。
6. **有异议先问**：拿不准某处算不算该加的，`AskUserQuestion` 反问，不要自己判断后顺手改。

违反（乱改其他东西、顺手优化、凭记忆重画丢字段）= 禁止交付。

## 前置：proto-spec（生成前强制路由，BLOCKER）
凡要画 / 改后台原型，**先加载 `proto-spec` 跑前置拆解**：
- 多页新建 → 出三件套（NAV-MAP / PUBLIC-SPEC / PAGE-SPEC）并经用户确认；
- 增量改 → 先跑 `SPEC-004` 影响判定（单页 / 全局：动 PUBLIC-SPEC token / style.css / 公共组件 / 影响其他页跳转 = 全局，须重跑全量 28 项 checklist + 真实浏览器点击）。
- `SPEC-002` 设计规范必须用户确认（色板 / token / 类型规范 / 视觉签名，禁"自动命中基线就默认采用"的兜底）；
- `SPEC-003` 导航地图登记门禁：任何 `go('xxx')` / 视图跳转先登记到 NAV-MAP，未登记禁止写进原型；
- `SPEC-005` 八项验收基线先立（布局对 / 视觉签名一致 / 避免 AI 默认风格 / 文案基调一致 / 跳转通 / 状态齐 / 交互真 / 无悬空）。
proto-c 同理已挂 SPEC-000 路由门禁，两端一致。

## 使用方式

0. **先找现成脚本（BLOCKER，见 PROTO-MOD-002）**：任何"截图 / 批量渲染 / 结构校验 / 复刻对图"动作，**第一步先查 `{SKILL_DIR}/scripts/`**，优先复用并按需扩参；**严禁新建一次性 `_xxx.js` / `_xxx.py`**。
   - 截图 / 复刻对图 → `scripts/regen_prd_shots.js`（`--proto`+`--map` 或 `--manifest`；`--width/--height` 对齐参考图尺寸；`sel:"body"` 整页、`sel:"#viewXxx"` 单视图）
   - 后台冒烟 → `references/proto_smoke.js`
   - **导出功能回归（CSV 真伪 / 列行数 / 无上限 / 全量）** → `scripts/test_export_csv.js`（`--proto` + `--click` + `--seed` 造数据 + `--expect-cols/--expect-rows/--expect-contains/--expect-absent/--dump`；0=PASS）
   - 平铺 → `scripts/gen_flat_modao.py` / `scripts/gen_flat_popup.py`
   - 脚本缺能力时**就地扩参**（保持向后兼容），不要在项目目录另起一个临时脚本
1. **读取规则**：`Read {SKILL_DIR}/rules.json`
2. **锁定模块**：`ux`（画/改原型）→ `smoke`（交付前门禁）→ `flat`（如需平铺产出）
3. **执行前置动作**：后台必须先走 **`PROTO-KB-001`（同域任务先确认本次是否沿用既有设计模板基座 —— 项目记忆里登记了模板就必须问，不许默认、不许跳轮次）** + `PROTO-STY-001`（确认后台参考页/基线）+ `PROTO-STY-005`（逐页/逐弹窗确认样式来源）；平铺必须先走 `PROTO-FLAT-001`（确定 mode）
4. **逐条比对 rules**：按 `module` 过滤，`BLOCKER` 一票否决
5. **交付前跑 checklist**：先跑 smoke 到退出码 0，再过 `checklist.items` 28 项；有平铺产出的另过 `flat_delivery_checklist` 8 项

## severity 语义

| 级别 | 含义 | 处理 |
|---|---|---|
| `BLOCKER` | 违反即事故 | 禁止交付，必须回头修 |
| `REQUIRED` | 必须执行 | 遗漏须补做后才能交付 |
| `ADVISED` | 建议遵循 | 可按场景裁量 |

## 模块

| module | 用途 | 规则前缀 | 关键 BLOCKER |
|---|---|---|---|
| `ux` | 后台交互原型 UX 约束（含 proto-spec 前置） | `PROTO-TXT` / `PROTO-STY` / `PROTO-STR` / `PROTO-KB` / `SPEC` | 含 PROTO-KB-001 设计模板沿用确认 / PROTO-STR-001 / PROTO-STY-004/005 / PROTO-STR-004 / SPEC-002 设计规范确认 / SPEC-003 导航地图登记 |
| `smoke` | 自动化冒烟测试硬门禁（后台脚本 `proto_smoke.js`，真实浏览器） | `PROTO-SMK` | 1 / 5 |

## 后台最易翻车的红线

1. **`PROTO-STR-001`** — 后台主体业务对象（列表/详情/商品/订单/优惠券/栏目等）的增改查一律跳转独立页，禁用 Modal 弹窗实现（grep `modal-overlay` 对主体增改查应零命中）；详情页也是独立 view。
   **两条例外**（2026-09-17 绿韵家水卡模板裁定）：① 复刻真实后台截图、截图中该操作本身就是弹窗（如「新增发货模板」「新增寄回地址」），或用户本次明确要求「点击新增打开弹窗」；② 维护的是表单内嵌配置项/模板（发货模板、寄回地址、水卡模板），不是独立业务对象。命中例外照做，但交付说明里要写明「哪一处是弹窗 + 依据哪条例外」；删除二次确认弹窗不受本条约束。
2. **`PROTO-STR-002`** — `viewXxx` 独立页必须写在 `<main>` 内，写在 `</main>` 外 → 点击跳转整页空白；靠 smoke 检查项 [A] 拦截。
3. **`PROTO-STY-004`** — 有真实后台截图时，侧栏/表头/按钮/筛选/状态 Tag 文案必须与截图逐字一致，不得凭旧原型记忆。
4. **`PROTO-STR-004`** — 后台为内部运营视角，所有用户标识字段均原文展示、不脱敏：手机号固定 11 位完整、昵称 / 真实姓名 / 用户ID 均原文直出，禁止星号遮蔽（如 `张*明`、`138****1234` 这类写法一律不得出现）。
5. **`PROTO-STY-005`** — 不能只找一个全局参考页就全盘套用，须逐页/逐弹窗确认样式来源。
6. **`PROTO-SMK-005`** — 交付后台原型前必须启动真实浏览器（playwright chromium）逐一点击所有导航/视图，确认每个视图真实可见（computed display≠none、有布局包围盒、有文本、祖先无隐藏）；jsdom 软渲染不查祖先隐藏，曾导致「漏闭合标签→后续视图被吞进隐藏容器→整页空白」事故，禁止用 jsdom 模式替代真实浏览器点击。
7. **`PROTO-FEAT-001`** — 禁止臆测/过度实现功能：严格按需求做，不擅自加需求未涵盖的 CRUD/交互（列表页额外加编辑/状态切换/批量/新增/排序/筛选等）；每个按钮/交互都能对应到一条明确需求，多出来的即删；需求不明确时先反问用户，不臆造（本条源于绿韵家素材管理「擅自加编辑+状态切换」被退回的复盘）。
8. **`PROTO-DEL-001`** — 所有「删除」操作必须二次确认：点击删除先弹确认（展示被删对象名称 + 「不可恢复」提示），确认才执行删除，禁止点击即删；须提供可复用的 `confirmAction(title,text,onOk)` 类帮助函数，所有删除入口统一调用，不得每处各写一套；适用于列表删除、批量删除、栏目/标签/词条删除等一切删除入口（本条源于绿韵家后台素材/栏目删除"点击即删"被要求补二次确认的复盘）。
9. **`PROTO-REPLICA-001`** — 有真实后台截图时遵循「参考图优先复刻工作流」：① 逐屏读全截图，列出「截图原有字段清单 + 功能入口清单」作为复刻基线；② 先严格 1:1 复刻截图现有字段与功能（只搬运不改）；③ 再读需求/口述变更，产出「变更清单」（新增/删除/修改字段、改/新增功能，逐项列）；④ 只按变更清单改，未列入的现有字段/功能一律保留，禁止顺手"优化/重做"；⑤ 交付前复查——逐字段追问来源，只允两类字段：**A 类=截图原有字段（在基线）**、**B 类=需求要求字段（在变更清单）**，其余即**臆造字段**，必须删除或反问确认后才留。交付前输出/核对「字段溯源表」（截图原有 / 需求新增）。这是 PROTO-FEAT-001「禁臆测」在有截图场景的落地，也是 2026-09-03「严格复刻只加功能」血泪教训的流程化（C 端同源见 proto-c）。
10. **`PROTO-DEL-002`** — AI 收到「删除某个元素」类修改指令时的执行五步法：① 先确认用户实际查看的是哪一份文件（同功能常有多副本：正式件/*.bak 备份/截图快照/gh-pages 线上），不默认当前文件；② grep 定位唯一锚点精准打点，只删该元素及其紧邻分隔符，禁整段/整行/整 tab 连带删（防页面被删秃）；③ 推线上后必须回读线上原文 grep 验证零命中才算完成；④ 元素若曾有相反裁定，最终裁定写入长期记忆裁定清单、禁止下轮翻案；⑤ 从备份/旧文件归并还原后，必须重跑全部历史删除清单回归（备份是删除前状态、天然带毒）。源于 2026-09-04 绿韵家「生成邀请码」按钮三连复盘（删错文件→归并复活→翻案保留→用户发火）。

11. **`PROTO-MOD-001`** — 原型增量修改「复制为主、只增不改」上位总纲：接到改原型需求默认以现有文件为基底做最小改动，只动需求明确的变更点，未列入变更清单的现有字段/选项/文案/结构/样式一律保留、像素级不动，禁止顺手优化/清理/重做/改文案/换组件；改完必做 diff 自检确认其余一致。覆盖 `PROTO-REPLICA-001`（有参考图）/ `PROTO-FEAT-001`（禁臆测），无论有无参考图都生效。违反 = 禁止交付。

12. **`PROTO-MOD-002`** — 机械性动作必须复用脚本，禁止新建一次性临时脚本：截图 / 批量渲染 / 结构校验 / 复刻对图，一律先 `ls {SKILL_DIR}/scripts/` 与 `references/`，复用既有脚本；**只差参数（如视口尺寸）就地扩参**（保持向后兼容），不另起 `_shot.js` / `_test.js` / `_push_*.py`。复刻对图用 `scripts/regen_prd_shots.js --width/--height`（对齐参考图像素）+ `sel:"body"` 整页截图，再用 PIL 上下拼图目视比对。违反 = 禁止交付（绿韵家曾堆出 16 个 `_push_*.py` 855 行重复逻辑；2026-09-14 又出现 `_shot_ws.js` / `_test_ws.js` 复现）。

13. **`PROTO-KB-001`** — 同域后台任务开工前必须确认「本次是否沿用既有设计模板基座」：项目记忆里登记了某类后台的设计模板（知识库参考模板 / 已定稿的基座 HTML，例：绿韵家商品后台 = ima 知识库「绿韵家项目/后台设计参考网址」+ 基座 `lvyunji-product-admin.html`）时，做同域页面（商品列表/详情/规格/库存/上下架等）前**先问一句**「这次 X 后台设计，沿用《X 设计模板》吗？」——答『是』先取参考再动手、取不到要如实说并降级到基座文件；答『否』问清新参考来源再动手。**每次都要问，不许以「上轮已确认」「同一批需求」跳过**；也不许不问就默认沿用、或另造一套样式。这是「先确认口径再动手」在模板复用场景的落地（2026-09-14 用户明确要求）。

## 交付前必答

- smoke 退出码是不是 0？
- `checklist.items` 28 项是否全绿（含后台专属 C19~C22、C-kb 设计模板确认）？
- 同域任务开工前，是否已按 `PROTO-KB-001` 确认过「本次是否沿用既有设计模板基座」？
- 有真实后台截图的，侧栏/表头/按钮/筛选/状态 Tag 是否逐字一致？
- 增改查是否全部独立页（grep `modal-overlay` 零命中）？若是表单内嵌配置弹窗或复刻真实后台已有弹窗，是否命中了 PROTO-STR-001 的两条例外、并在交付说明里写明依据？
- 本页每个按钮/交互/字段是否都有明确需求出处、无需求未覆盖的臆测功能（编辑/状态切换/批量/新增等），多出来的已删（PROTO-FEAT-001）？
- 有参考截图时，是否走了「参考图优先复刻工作流」：先 1:1 复刻截图 → 再按需求变更清单改 → 交付前做了「字段溯源表」复查，只保留「截图原有 + 需求要求」两类字段、无臆造字段（PROTO-REPLICA-001）？
- 本页所有删除入口是否都先弹二次确认（展示对象名 + 不可恢复提示）、确认才执行，且复用统一 confirmAction 组件（无点击即删）（PROTO-DEL-001）？
- 删除类修改指令是否走了五步法：确认用户所看文件 → 精准打点 → 推线上回读零命中 → 裁定入长期记忆 → 归并还原后重跑历史删除回归（PROTO-DEL-002）？
- 全局函数名有没有与宿主/DOM 元素属性同名（scrollTop / click / open / close / focus / remove / content / text / value / title / name / width / height 等）？内联 onclick 的作用域链里元素自身属性会遮蔽同名全局函数 → 点击抛 TypeError 且静默失效（整站不崩、肉眼难发现）；全局函数一律带业务前缀，冒烟 [E] 段运行期错误必须为 0（PROTO-NAM-001）？
- 用户标识字段（手机号 / 昵称 / 真实姓名 / 用户ID）是否均原文未脱敏（无星号遮蔽）？
- 有平铺产出的，mode 定了吗？顶部标「无交互」了吗？
- 多页新建是否先跑 proto-spec 出三件套并确认设计规范？增量改是否先判单页/全局（SPEC-004）？
- 设计规范（色板/token/视觉签名）是否经用户逐项确认、无兜底默认（SPEC-002）？
- 所有 `go()` 跳转是否都登记在 NAV-MAP、无未登记跳转（SPEC-003）？
