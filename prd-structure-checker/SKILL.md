# PRD 结构排查器（prd-structure-checker）

## 用途

对照团队《产品需求文档（PRD）输出规范与标准示例（修订于260715）》的骨架，
对一份 PRD / 需求文档终稿做**结构完整性排查**。核心规则只有一条：
**必含板块只能多不能少**——终稿必须覆盖规范中的全部板块（一~九），缺失任一即不通过；
额外板块允许存在。凡是缺失、单薄或未知的内容，**必须反问用户补充，不得由模型凭空生成**。

本 skill 是**全局强制规则**：任何任务只要产出/审阅/修订“需求文档 / PRD”，
都必须先调用本 skill 完成结构排查，通过后才能定稿或进入评审。

## 何时使用

- 用户要求写、改、审一份 PRD / 需求文档 / 产品需求说明书。
- 用户说“帮我出 PRD”“润色需求文档”“检查这份 PRD 缺不缺东西”“终稿排查”。
- 任何以“需求文档”“功能需求”“产品方案”为交付物的任务收尾阶段。
- 即在对话中未明说，只要产物是 PRD 类文档，也强制触发本排查。

## 排查流程

1. **加载规范依据**：读取 `references/prd-structure.md`，掌握必含板块 一~九 及其关键子项。该文件是判定唯一依据。
2. **获取终稿**：接收 PRD 文件路径或全文内容。若用户在对话中直接给出文本，先落盘为 `.md` 再排查。
3. **跑结构扫描（四阶段）**：用 `scripts/check_prd.py` 对文档做确定性扫描。
   ```bash
   python scripts/check_prd.py 路径/到/PRD文档
   ```
   - **阶段1（结构存在性）**：一~九 必含板块是否出现，缺失即不通过。
   - **阶段2（§四 内容深度）**：对功能需求详情做"模板式详清"扫描，逐项判定
     `需求影响范围 / 涉及终端明细 / 界面设计·原型截图 / 交互说明 / 字段明细表 /
     功能按钮权限表 / 逐步操作逻辑 / 查询条件规格 / 业务逻辑·计算规则 / 边界条件 / 数据来源标注`
     是否齐备；缺失超过阈值（默认 3 项）判为 **⚠️ 结构通过但深度单薄**，并列出缺失子项。
     这一步能拦住"扁平一行摘要表"蒙混过关（详见 `references/prd-structure.md` 的 D 板块详清规范）。
   - **阶段3（待确认扫描）**：列出全文「待确认/需确认/TBD/待补充」标记，提醒澄清或保留占位，禁止编造填充。
   - **阶段4（红线与图文一致性）**：自动扫描 ①越界红线词（用户裁定不纳入的端口/能力须有"不涉及"豁免声明）②待确认项悬空（引用字段正文未定义）③埋点表是否符合《泰小虎埋点表v2.3》双表或已链接引用独立文档 ④图文一致性人工核对清单。详见下方「阶段4」章节。
   将脚本输出作为初判，再结合人工（模型）判断修正“单薄 ⚠️”项。
4. **逐板块定级**：对照 `references/prd-structure.md` 把每个板块定为三类之一：
   - ✅ 完整：板块存在且含关键子项，内容非占位。
   - ⚠️ 单薄：板块存在但缺关键子项，或内容为空泛占位（如“待补充”“TBD”“详见xxx”无实质）。
   - ❌ 缺失：终稿完全找不到该板块或其等价表述。
5. **强制反问补充（核心，不可跳过）**：对每一个 ❌ 缺失 或 ⚠️ 单薄 的板块：
   - **禁止臆造**：不得替用户编内容填空。
   - **直接反问**：用 `AskUserQuestion` 或清晰的追问，列出该板块“具体缺什么”，请用户补充。
   - 一次性可合并多个缺失项提问，但每项都要指明缺的内容（如“缺‘状态机与状态流转规则’：请补充涉及状态变化的实体及其流转表”）。
   - 用户补充或**明确声明该项不适用/可省略**后，才将该项标记为已处理；用户未确认前不得定稿。
6. **输出排查报告**：按以下格式汇总（可直接呈现给用户）：

   ```
   # PRD 结构排查报告
   文档：（文档名）
   结论：通过 / 不通过（缺失 N 项）/ ⚠️ 结构通过但 §四 深度单薄

   ## 阶段1：一~九 必含板块存在性
   | 必含板块 | 状态 | 命中关键词 |
   | 一、文档基本信息 | ✅ | 含修订记录表 |
   | 四、功能需求详情 | ✅ | 功能需求详情 |
   | ... | ... | ... |

   ## 阶段2：§四 功能需求详情 — 内容深度检查
   | 深度子项 | 状态 | 命中关键词 |
   | 页面原型与交互示意 | ✅ | 原型、figure |
   | 界面与展示规则(字段表/按钮权限) | ✅ | 字段名称、权限 |
   | 业务逻辑与边界条件(逐步操作逻辑) | ❌ 缺失 | — |
   | ... | ... | ... |

   待补充（已向你反问）：
   - 三、业务流程与架构·状态机：请补充订单/券的状态流转（起始状态+动作+条件=目标状态）
   - §四 逐步操作逻辑：请补充各功能的"前置条件→步骤→异常分支"
   - 七、关键边界设计检查清单：未找到逆向流/退款自检，请补充
   ```

7. **定稿门槛**：仅当所有必含板块均为 ✅（或用户明确豁免）时，方可判定“通过”并允许定稿/进入评审。

## 输出风格：简洁优先

本 skill 要求结构完整、字段细化、不确定性明确标注，但**不要求冗长**。写 PRD 时应遵循：

1. **能删则删**：删除与当前功能无关的背景铺垫、重复解释、过度修饰的过渡句。背景控制在 1-2 段，目标/指标用表格逐行呈现。
2. **用什么 + 条件/规则即可**：每个功能小节以「做什么」和「有什么条件/规则」为核心，避免大段叙事。逐步逻辑用编号步骤，异常分支用 bullet。
3. **表格承载细节**：字段映射、验收标准、边界条件、权限、埋点等尽量用表格，减少散文式描述。
4. **不确定项集中标注**：用「⚠️ 待确认 @干系人」一句话占位，不要展开解释为什么不确定。
5. **禁止为凑篇幅而扩写**：结构板块只能多不能少，但每个板块内部内容应精简到可开发/可评审所需的最小信息量。
6. **纯后端/接口契约 PRD 的例外**：若 PRD 明确不涉及前端界面（如仅定义后端接口、数据交互规则、Webhook 回调），可在 §四 中用一个简短「范围声明」列出不适用的前端深度子项（如界面设计/原型截图、交互说明、前端字段明细表、功能按钮权限表），并注明由哪份既有需求覆盖。结构排查时这些关键词会被命中，视为已声明。

## 关键边界（来自规范宗旨）

- 宁多勿漏：宁可多写，不可漏板块。
- 多端联动：涉及用户/运营/商家须全链路闭环，警惕“断头需求”。
- 凡变必录：变更须有版本记录并高亮 @ 干系人。

## §四 细节书写标准（强制套用《物流费用账单 V2.10.3》模板）

写 PRD 的 **§四 功能需求详情** 时，不允许写一段扁平摘要，必须按 `references/prd-detail-template.md` 的范本**逐功能点**拆解。要点：

1. **逐功能点拆分**：以业务对象为顶层，向下拆成「状态流转 → 权限 → 列表 → 功能按钮总表 → 每个按钮独立小节 → 编辑/新增表单 → 查询条件 → 菜单权限」。**一个按钮 = 一个独立小节**。
2. **列表字段表**：字段名称 / 需求说明 / 备注，并单列排序、分页、合计行、数据唯一判断。
3. **按钮四要素 + 逐步逻辑**：每个按钮写「功能说明 / 显示位置 / 权限 / 前置条件 / 功能实现」，功能实现必须含逐步逻辑 + 异常分支 + **校验提示文案**（如未勾选→“请选择数据”、勾选已确认→“仅未确认支持确认”）。
4. **编辑/新增表单**：按区域分组（区域/字段/功能逻辑说明/备注），每个字段写明输入限制（必填/类型/长度/小数位），并列出**计算公式**。
5. **查询条件**：查询条件 / 查询说明（控件类型 / 选项来源 / 查询行为）。
6. **字段级数据来源**：列表字段须标注「取《XX表》字段」「调 XX 接口」，区分前端本地 / 后端 / 第三方。
7. **计算公式 + 数据演练**：复杂计算须附具体数字演练并保证合计守恒。
8. **逐页截图**：每个页面一张图（列表/编辑/弹窗），图文对得上；禁止用流程 SVG 充当界面截图。

> 阶段2 深度扫描（见 `scripts/check_prd.py` 的 `DEPTH_ITEMS`）即按上述 8 项判单薄；
> 缺失超 3 项 → 结论判为「⚠️ §四 深度单薄」并列出缺失项，触发向用户反问补充。

## 不确定性处理与反问机制（核心红线，不可跳过）

写 §四（以及任何板块）遇到不确定数据时，**第一反应不是编，而是问或标**。

**写之前**：先逐页面/逐功能点梳理「已知 vs 未知」，列出所有不确定点。凡属以下任一，即视为「不确定数据」，禁止臆测：
- 字段长度 / 输入限制 / 格式未指定；
- 按钮权限角色 / 数据范围未定义；
- 计算公式 / 分摊 / 状态流转未明确；
- 字段来源（前端 / 后端 / 第三方）不清楚；
- 异常提示文案、边界值未给；
- 任何「我觉得应该是…」「先这样占位」的假设。

**处理方式（二选一或并用）**：
1. **文档内占位**：以「⚠️ 待确认 @干系人」明确标注（模仿模板「具体逻辑需 @Lven 确认」），绝不编造内容填进去；
2. **主动反问**：用 `AskUserQuestion` 反问**具体、可落地**的问题（例：「XX 字段的输入长度限制是多少？」「未确认状态点击删除的提示文案是什么？」），拿到确切答案后再写。

**写之后**：必须向用户汇总「本次有 N 处待确认项，已标注/已提问」，不可静默带过。
若用户坚持先占位：只允许「⚠️ 待确认 @干系人」占位，**禁止编数值**。
阶段3 扫描（见脚本）会检测全文「待确认 / 需确认 / @X确认 / TBD / 待补充」等标记并列出，提醒澄清或保留占位。

## 阶段4：红线与图文一致性扫描（自动检查项，沉淀自评审踩坑）

本阶段目的是**从源头挡住「直播挂车」需求评审中暴露的四类问题**：图文臆造、范围外内容误入、埋点不规范、待确认悬空。脚本在阶段3 之后自动执行，输出四类告警。

### 4.1 红线词扫描（RED_LINE）
- **词库**：商家端后台 / 商家端 / 回放 / 火山SaaS / 火山 SaaS / SaaS配置 / 火山引擎直播配置 等（用户已裁定不纳入本项目的端口/能力）。
- **判定**：红线词出现时，若前后 30 字内**无**「不涉及 / 不在范围 / 排除 / 不配置 / 不开放」等豁免声明 → 告警。
- **处理**：若确为范围外，必须在文中明确写「本需求不涉及XX」；禁止把红线词当作功能实现描述写进 PRD。

### 4.2 待确认溯源（UNCERTAIN_TRACEABILITY）
- **判定**：提取每个「⚠️ 待确认 @干系人：<事项>」中引号「」/"" 内的字段名，若该字段**全文仅出现 1 次**（即只在待确认处、正文未定义）→ 告警"疑似悬空"。
- **根因**：本次「选品弹窗运营类型/品牌分类」待确认引用的字段正文根本不存在，属"先脑补字段再脑补待确认"。
- **处理**：删掉悬空待确认；或先在被引用处（如字段表）定义该字段再保留待确认。

### 4.3 埋点规范（TRACKING_V2_3）
- **判定**：PRD 含埋点内容时，若已链接引用《泰小虎埋点表v2.3》独立文档/在线规范 → 通过；否则须为 v2.3 双表（命中核心列≥12）→ 通过；若仅为 5 列简化版（所属终端/所在页面/事件名称/触发时机/上报参数）→ 告警。
- **处理**：改为 v2.3 双表，或拆成独立 HTML 后在 PRD 用链接引用（推荐，避免文档臃肿）。

### 4.4 图文一致性（DIAGRAM_CONSISTENCY）
- **判定**：检出「流程图/范围图/状态机/架构图」等图说关键词后，输出一份**人工核对清单**（图内文字不可直接解析）。
- **清单要点**（即本次踩坑项）：
  1. 流程图节点须与正文主流程逐条对应，不含正文未定义的功能（如仅"同步"却画"创建直播间"）；
  2. 影响范围图依赖系统须与正文"数据层/第三方依赖"逐条对应，不含正文未列出的依赖（如"用户账号/画像""商城订单""优惠券模块"）；
  3. 状态枚举须对接真实接口文档枚举值，禁止假设（如"违规下播"若接口无此值则须删除）；
  4. 图中出现的字段/概念须在正文有定义。
- **红线提醒**：生成任何图（流程图/范围图/状态机）后，**必须回读图内文字与正文逐条比对**，禁止脑补节点。

### 4.5 业务流程图一致性（FLOW_DIAGRAM_CONSISTENCY）🔴
- **前置规则（写 PRD 前必须满足）**：
  1. **必须先有已梳理确认的业务流程图**才能开始写 PRD §三。推荐格式：**横向泳道全链路图**（按端口/角色分泳道，按阶段分列，如 制券→配置→发放→领券→核销）。
  2. 若尚未梳理流程图 → **必须先停止写 PRD**，先画出业务流程图经用户确认后，再基于该图画 PRD。
  3. **📌 流程图必须从需求梳理文件获取**（2026-07-28 固化）：PRD §三的业务流程图应直接引用/嵌入「需求梳理阶段」产出的权威流程图文件（如 `XX-需求梳理图集.html`），**禁止在 PRD 中独立重绘与梳理文件不一致的流程图**。
     - 正确做法：在 PRD 流程图章节顶部标注 `📎 权威来源：《XX-需求梳理图集.html》§X`，SVG 内容与梳理文件保持一致（可原样复制或截图嵌入）。
     - 如需修改流程图 → **必须先修改需求梳理文件中的原图 → 再同步更新到 PRD**，不可只在 PRD 里改而不同步回梳理文件。
     - loop 排查检测到 PRD 流程图与梳理文件不一致时 → 按 Auto-Fix 规则（§4.10）直接替换为梳理文件版本，不确认。
- **判定**（check_prd.py 自动扫描）：
  - 🔴 **必须修**：PRD 检测到 `<svg>` / `<img>` 流程图，但流程图附近（±600 字）无以下基线声明关键词：
    `已梳理` / `横向泳道` / `泳道图` / `与.*流程图一致` / `依据.*梳理` / `本图与`
  - 🔴 **必须修**：PRD 有「业务流程图」章节标题但无任何图形内容
  - 🟡 **建议查**：图中提取的节点词对正文功能模块覆盖率 < 50%
- **修正方式**：
  - 若已有已梳理的泳道流程图 → 在 PRD 流程图旁标注
    「本图与《XX业务流程图（横向泳道·制券→核销全链路）》一致，
    节点/阶段/泳道一一对应」；
  - 若无已梳理图 → **撤回 PRD 流程图**，先补画横向泳道全链路图经确认后再重画。
- **踩坑背景**：优惠券需求 PRD 的 3.2 流程图为简化线性图（7 节点），
  与已梳理的横向泳道全链路图（4 泳道 × 5 阶段 × 15+ 节点）严重偏离——
  缺少制券模板库、发券引擎、券服务后台、火山引擎 API、数据看板等关键环节，
  且未按端口分泳道。

### 4.6 状态机完整性（STATE_MACHINE）🔴
- **判定**（check_prd.py 自动扫描，检出「状态机/状态流转」关键词后激活）：
  - 🔴 **必须修**：
    1) **宽泛起始状态**：状态转换表含「任意→删除」「任意→下架」等 → 缺状态守卫。
       每个破坏性操作须限定合法起始状态（如仅「下架」可「删除」，「启用」须先「下架」）。
    2) **破坏性操作前置条件过弱**：删除/作废/回滚的前置条件仅写
       「确认弹窗」「运营操作」→ 缺业务前置条件（无已发放券/无关联活动/先下架）。
    3) **循环/同态转换**：`启用→下架 目标=下架` 或 `A→操作→A` → 可能写反。
    4) **原型操作列缺按钮**：原型列表有「删除」但无「下架/启用/编辑」等状态变更按钮
       → 原型与状态机不对应，用户无法在 UI 上执行中间状态转换。
  - 🟡 **建议修**：
    5) 有转换表但未定义「完整状态枚举」（所有可能状态值的集合）。
    6) 子实体（发券活动/领券活动/用户券）的状态机仅为简短文字描述（<80字），
       未扩展为表格格式。
- **写 PRD 时必须逐条确认**（check 前 self-check 清单）：
  1. ✅ 原型列表操作列是否包含状态机定义的所有状态变更操作？
     （特别是下架/启用/停用/发布/撤回——不能只有查看+删除）
  2. ✅ 每个破坏性操作（删除/作废/回滚）是否有**业务级前置条件**？
     （不是仅"确认弹窗"，而是如"必须先下架"+"无已发放券"+"无进行中活动"）
  3. ✅ 状态枚举是否完整列出？边界状态（草稿/过期/锁定期）是否覆盖？
  4. ✅ 原型中每个操作按钮是否有关联的逐步逻辑？（含异常分支+校验提示文案）
- **踩坑背景**：优惠券 PRD 3.4 状态机表存在：
  - 「新建(默认启用)→下架→运营操作→下架」循环/同态；
  - 「任意→删除→确认弹窗→已删除」无业务守卫；
  - 原型操作列仅有「查看+删除」，缺「下架/启用/编辑」按钮；
  - 删除逻辑 `confirm→filter→toast` 无任何前置校验。

### 4.7 功能范围标注：已有 vs 新增/改动（SCOPE_TAGGING）🔴
- **规则（写 PRD §四 时强制）**：
  1. **比对需求梳理的范围**：动笔前先确认本期涉及的端口/功能，哪些在既往版本中<b>已存在</b>、哪些是<b>本期新增/改动</b>。
  2. 每个功能点（页面/模块/子功能）必须标注其一：
     - <span class="tag r">已有-沿用</span>：既往已存在的功能 → **仅写一句「沿用现有功能，详见原型 XXX.html」**，**禁止展开字段表/按钮表/逐步逻辑**（业务逻辑闭环在原型，PRD 不赘述）。
     - <span class="tag y">本期新增</span> / <span class="tag g">本期改动</span>：才逐功能点详写（字段表/按钮逻辑/表单/查询/数据来源）。
  3. **平台端与商家端是独立后台**：各自的新增/编辑/下架/删除是各系统原生功能，UI 无需对比统一或刻意区分。
  4. **删除/下架等破坏性操作若是已有功能**，同样仅标「沿用现有功能」，不重复展开细节；仅当本期对其有新增规则（如违规下架弹窗必填原因）才在对应行补述。
- **判定**（check_prd.py 自动扫描，检出「四、功能需求」章节后激活）：
  - 🔴 **必须修**：§四 下某个功能点（h3/h4 标题）**无任何范围标注**（无「已有/沿用/新增/改动/沿用现有功能」等关键词）→ 须补标。
  - 🟡 **建议查**：某功能点写了「沿用现有功能」却仍展开了大段字段表/逻辑 → 冗余，应压缩为一句。
- **踩坑背景**：优惠券 PRD 初版把平台端「新增/编辑/下架/删除」的字段表、按钮权限表、表单字段全量展开，
  但这些都是 gruul-mall 优惠券 addon 的<b>已有功能</b>（平台端原生能力），
  用户在评审中明确要求「已有功能不要在 PRD 里赘述，PRD 只要说一句沿用现有功能就行，
  只写本期新增或改动的功能」。后据此重建规则：§四 每个功能点强制标 已有-沿用 / 本期新增 / 本期改动。

### 4.8 埋点必要性自检（TRACKING_NECESSITY）
写 PRD 埋点清单（§五 本期涉及事件）时，每个候选事件必须能回答"为什么必须客户端埋点"，否则不纳入：
- **不埋①**：纯页面/组件内交互（如 Tab 切换、折叠展开、滚动到底）且无业务分析价值 → 不埋；若确需看各 Tab 曝光分布，用页面曝光事件带"当前Tab"参数即可，不单独建切换事件。
- **不埋②**：结果类/汇总类数据（如核销结果、领取成功结果、支付结果）若后端业务表（核销流水、发放记录、订单表）已落库、可直接统计 → 不重复做客户端埋点，避免双源口径不一致。
- **需埋**：用户行为意图（点击领券/点击购买/弹窗曝光关闭/进入某页）、且后端无法直接还原的事件才埋。
- **踩坑**：优惠券需求初稿曾把 `my_coupons_tab_switch`（券包Tab切换）、`coupon_redeem_result`（用券核销结果）列入埋点清单，经评审裁定移除——前者无分析价值、后者后端核销流水表可直接统计。

### 4.9 待确认项卫生 + 状态机前后矛盾（PENDING_HYGIENE）🔴
写 PRD 时，**待确认项（⚠️ 待确认 @干系人）不是"把矛盾丢给评审"的容器**。以下两类必须写 PRD 阶段就地 resolve，不得作为待确认项甩出：
- **不得与「设计如此」决策冲突**：若正文已裁定某项为既定设计（如"无重新上架/启用路径，下架即终态""编辑不允许变相上架"），则**不得**再把它写成待确认项（典型反面："⚠️ 待确认：编辑能否变相上架已下架的券？"）。这类问题应直接写成设计说明，结尾标注"（非待确认）"。
- **不得与现有/沿用功能冲突**：已标「已有-沿用」的功能（如平台端券的新增/编辑/下架/删除），其行为是否允许/限制由既有实现决定，**不要**就既有功能的核心行为提"是否允许/可否"类待确认项；若确属本期新增/改动，必须标「本期新增」并写清规则，而非含糊待确认。
- **状态机不得前后矛盾**：同一状态机转换表中，某起始状态**既**在其它行声明"无编辑 / 编辑已替换 / 无编辑需求"，**又**保留该状态的「编辑」行 → 直接矛盾。终态若禁止变相上架，应**直接删除编辑行**，而非同时保留编辑行与"无编辑"声明。（优惠券 PRD v1.0.7 实测：已下架行既写"编辑替换为删除、无编辑需求"又写"已下架→编辑 原型已有"，即此类矛盾，已删除编辑行修复。）
- 扫描器 `scan_pending_hygiene()` 自动覆盖：① 状态机转换表同状态"无编辑声明 vs 编辑行"冲突、同(状态,动作)映射不同目标；② 待确认项含"变相上架/重新上架"类提问且非否定语境。

### 4.10 Loop 自动修复模式（Auto-Fix）

**核心规则：loop 排查发现的问题，能直接修的不要让用户确认，直接改。**

#### 适用范围（可自动修复，无需确认）

| 问题类型 | 判定标准 | 修复动作 |
|---|---|---|
| **待确认项残留** | 可基于已有裁定/合理推断直接决定（如"商家端是否开放看板"→原型未做+商家端不需全平台看板→裁定不开放） | 改为明确标注，同步清理 §四 warn 块 + §九 汇总 |
| **状态机宽泛起始状态误报** | 匹配到非状态机上下文的关键词（如"全部功能模块""全部会员""全部店铺"） | PRD 文案微调（换近义词）+ 检测器加上下文过滤 |
| **流程图覆盖度不足** | 缺少明确的客户端入口节点（如商品详情领券） | 补全 SVG 节点 + 更新 smoke 说明文字 |
| **表格中 ⚠️ 待确认** | 属于已有功能沿用/不开放类决策 | 改为 ✓ / — + 小字注释说明理由 |
| **前后矛盾** | 同一事实在 PRD 两处表述冲突（如"已下架无编辑" vs "已下架→编辑"） | 保留与设计意图一致的版本，删除矛盾版本 |

#### 不适用范围（必须人工确认）

| 问题类型 | 原因 |
|---|---|
| **业务决策类** | 需要干系人拍板的功能取舍（如"是否支持 XX 场景"）|
| **KPI 阈值 / SLA** | 需要运营/管理层确定的具体数值 |
| **API 接口契约** | 需要技术 Owner 定义的字段/鉴权逻辑 |
| **外部依赖确认** | 需要第三方系统配合的集成方案 |

#### 执行流程

1. 跑 `check_prd.py` 完整扫描
2. 逐条审查阶段4 输出：
   - 若属「适用范围」→ **直接改 PRD** + 在版本记录中注明 `auto-fix: {问题描述}`
   - 若属「不适用范围」→ 保留为待确认项 @干系人
3. 复跑 loop 确认告警数下降
4. 推送 GitHub Pages

> **踩坑记录**：优惠券 PRD v1.0.7→v1.0.8 一次性修复了 4 类 loop 问题（状态机误报/表格待确认/流程图覆盖度/检测器精度），全部基于本规则直接执行未打断用户确认。

### 4.11 表格 CSS 视觉错位检测（TABLE_VISUAL_MISALIGN）🔴🟡
- **问题本质**：HTML 结构正确（列数匹配）但 **CSS 渲染层错位**——`<td>` 内含 `<br>` + 长文字在 `width:100%` 表格中撑爆列宽，导致整表视觉错位。`scan_table_quality` 原仅检测结构层，**完全漏掉此类问题**。
- **新增 3 项检测**（`scan_table_quality` 阶段4 扩展）：
  1. 🟡 `<td>` 含 `<br>` + 长文字（>12 字）→ 撑列风险，建议缩短文案或加 CSS 控制
  2. 🔴 `<table>` 缺 `table-layout:fixed` **且** 存在长内容 td → **高错位风险**，必须加 `table-layout:fixed` + `word-break:break-all`
  3. 🟡 单个 `<td>` 纯文本超长（>40 字）→ 建议折行或精简
- **Auto-Fix 修复方式**（适用范围，直接改不确认）：
  1. 全局 CSS 加 `table-layout:fixed` + `th,td{word-break:break-all;overflow-wrap:break-word}`
  2. 缩短 td 内长注释文字（如「不开放（商家端仅管自身券，无需全平台看板）」→「不开放（商家端仅管自身券）」）
  3. 超长纯文本 td（>40 字）拆行或用小字 span 缩减
- **踩坑**：优惠券 PRD §3.1 范围映射表 HTML 列数 6=6 完全正确，loop 报「✅ 全部表格结构正常」，但截图明显错位——根因是 `table{width:100%}` 无 `table-layout:fixed`，td 内 `—<br><span>不开放（商家端仅管自身券，无需全平台看板）</span>` 把商家端后台列撑爆。

### 4.12 多列表格列宽挤压检测（TABLE_COL_SQUEEZE）🔴
- **问题本质**：`table-layout:fixed` + 多列（≥5）表格 + 无 `<colgroup>` 显式列宽 = 浏览器均分列宽 → 首列长文本（如"优惠券管理（列表/新建/详情）"）+ 单元格内 `<br>` 标签 = **所有内容视觉上挤到一列**。结构层完全正确（thead/tbody/tr/td 列数匹配），但渲染层崩塌。
- **检测规则**（`scan_table_quality` 新增第 11 项）：
  - 表格 ≥ 5 列 且 全局 CSS 含 `table-layout:fixed` 且 该表无 `<colgroup>` → 🔴 必须修
- **修复方式**（Auto-Fix，直接改不确认）：
  1. **首选**：给该表加 `<colgroup><col style="width:X%">…</colgroup>`，首列分配更宽比例（如 22%），其余列均分剩余
  2. **备选**：将该表的 `table-layout` 覆盖为 `auto`（内联 style 或 scoped class）
  3. 同时缩短单元格内长注释文字（font-size 缩到 10px）
- **踩坑**：优惠券 PRD v1.0.10 的 §3.1 范围映射表（6 列：功能模块/平台端后台/商家端后台/App/小程序/独立H5），全局 `table-layout:fixed` 导致每列仅 ~16.7%，首列 "优惠券管理（列表/新建/详情）" 加上各 cell 的 `<br><span>新建无店铺选择</span>` 直接把整表挤成一列堆叠。v1.0.11 修复：加 `<colgroup>` 7 列显式宽度 + 全局改回 `table-layout:auto`。

### 4.13 流程图防篡改保护（FLOW_DIAGRAM_TAMPER_PROOF）🔴
- **核心规则**：PRD §三 业务流程图**必须原样引用/嵌入已确认的权威流程图文件**（如 `coupon-flow.html` / `需求梳理图集.html`），**禁止 AI 自行简化、重绘、修改、省略节点或泳道**。
- **权威来源声明要求**：
  1. 流程图章节顶部必须标注 `📎 权威来源：《XX文件名》（含线上链接）`
  2. 必须包含约束声明：「⚠️ 禁止在 PRD 中自行简化/重绘/修改流程图。如发现差异须报用户确认后才可修改——AI 无权擅自改动」
  3. 若权威源含多张图（泳道图+时序图A+B），PRD 必须**全部内嵌或全部链接**，不得只选一张简化版
- **检测规则**（`scan_flow_diagram_consistency` 新增第 5 项）：
  - 🔴 有 SVG 但无权威来源引用（coupon-flow / 需求梳理图集 / 横向泳道 / 全链路）→ 告警
  - 🔴 引用了 coupon-flow.html 但图中无泳道关键词（平台端后台/商家端后台/券服务/火山引擎/用户端）→ 疑似被简化，必须回退完整版
  - 🟡 有 SVG 但无「禁止自行修改」约束声明 → 建议添加
- **差异报告机制**：
  - 当 loop 排查发现 PRD 流程图与权威源不一致时，**必须**：
    1. 停止任何自动修复
    2. 向用户列出具体差异（哪些节点/泳道/时序图缺失或被简化）
    3. 等待用户确认后才能修改
    4. 用户确认后，同步更新权威源文件（若用户要求改的是权威源本身）
- **踩坑**：优惠券 PRD v1.0.10 的 §3.2 流程图为自绘的简化 6 阶段线性图（触达领券→卡包到账→适用浏览→下单抵扣→分享裂变→边界异常），丢失了 `coupon-flow.html` 中的：
  - ① 整体业务泳道图（6 泳道：平台端后台/商家端后台/券服务·后端/火山引擎/用户端，5 阶段 × 15+ 节点）
  - ② 时序图 A：直播时长发券（运营→平台端→券服务→火山引擎→用户端，10 步）
  - ③ 时序图 B：商详领券→下单核销→关单返还（13 步 + alt 分支）
  
  v1.0.11 已回退为完整嵌入 coupon-flow.html 三张原图。
