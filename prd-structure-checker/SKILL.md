# PRD 结构排查器（prd-structure-checker）

## 用途

对照团队《产品需求文档（PRD）输出规范与标准示例（修订于260715）》的骨架，
对一份 PRD / 需求文档终稿做**结构完整性排查**。核心规则只有一条：
**必含板块只能多不能少**——终稿必须覆盖规范中的全部板块（一~九），缺失任一即不通过；
额外板块允许存在。凡是缺失、单薄或未知的内容，**必须反问用户补充，不得由模型凭空生成**。

本 skill 是**全局强制规则**：任何任务只要产出/审阅/修订“需求文档 / PRD”，
都必须先调用本 skill 完成结构排查，通过后才能定稿或进入评审。

## 何时使用

- 用户要求写、改、审一份 PRD / 需求文档 / 产品需求说明书。
- 用户说“帮我出 PRD”“润色需求文档”“检查这份 PRD 缺不缺东西”“终稿排查”。
- 任何以“需求文档”“功能需求”“产品方案”为交付物的任务收尾阶段。
- 即在对话中未明说，只要产物是 PRD 类文档，也强制触发本排查。

## 排查流程

1. **加载规范依据**：读取 `references/prd-structure.md`，掌握必含板块 一~九 及其关键子项。该文件是判定唯一依据。
2. **获取终稿**：接收 PRD 文件路径或全文内容。若用户在对话中直接给出文本，先落盘为 `.md` 再排查。
3. **跑结构扫描（四阶段）**：用 `scripts/check_prd.py` 对文档做确定性扫描。
   ```bash
   python scripts/check_prd.py 路径/到/PRD文档
   ```
   - **阶段1（结构存在性）**：一~九 必含板块是否出现，缺失即不通过。
   - **阶段2（§四 内容深度）**：对功能需求详情做"模板式详清"扫描，逐项判定
     `需求影响范围 / 涉及终端明细 / 界面设计·原型截图 / 交互说明 / 字段明细表 /
     功能按钮权限表 / 逐步操作逻辑 / 查询条件规格 / 业务逻辑·计算规则 / 边界条件 / 数据来源标注`
     是否齐备；缺失超过阈值（默认 3 项）判为 **⚠️ 结构通过但深度单薄**，并列出缺失子项。
     这一步能拦住"扁平一行摘要表"蒙混过关（详见 `references/prd-structure.md` 的 D 板块详清规范）。
   - **阶段3（待确认扫描）**：列出全文「待确认/需确认/TBD/待补充」标记，提醒澄清或保留占位，禁止编造填充。
   - **阶段4（红线与图文一致性）**：自动扫描 ①越界红线词（用户裁定不纳入的端口/能力须有"不涉及"豁免声明）②待确认项悬空（引用字段正文未定义）③埋点表是否符合《泰小虎埋点表v2.3》双表或已链接引用独立文档 ④图文一致性人工核对清单。详见下方「阶段4」章节。
   将脚本输出作为初判，再结合人工（模型）判断修正“单薄 ⚠️”项。
4. **逐板块定级**：对照 `references/prd-structure.md` 把每个板块定为三类之一：
   - ✅ 完整：板块存在且含关键子项，内容非占位。
   - ⚠️ 单薄：板块存在但缺关键子项，或内容为空泛占位（如“待补充”“TBD”“详见xxx”无实质）。
   - ❌ 缺失：终稿完全找不到该板块或其等价表述。
5. **强制反问补充（核心，不可跳过）**：对每一个 ❌ 缺失 或 ⚠️ 单薄 的板块：
   - **禁止臆造**：不得替用户编内容填空。
   - **直接反问**：用 `AskUserQuestion` 或清晰的追问，列出该板块“具体缺什么”，请用户补充。
   - 一次性可合并多个缺失项提问，但每项都要指明缺的内容（如“缺‘状态机与状态流转规则’：请补充涉及状态变化的实体及其流转表”）。
   - 用户补充或**明确声明该项不适用/可省略**后，才将该项标记为已处理；用户未确认前不得定稿。
6. **输出排查报告**：按以下格式汇总（可直接呈现给用户）：

   ```
   # PRD 结构排查报告
   文档：（文档名）
   结论：通过 / 不通过（缺失 N 项）/ ⚠️ 结构通过但 §四 深度单薄

   ## 阶段1：一~九 必含板块存在性
   | 必含板块 | 状态 | 命中关键词 |
   | 一、文档基本信息 | ✅ | 含修订记录表 |
   | 四、功能需求详情 | ✅ | 功能需求详情 |
   | ... | ... | ... |

   ## 阶段2：§四 功能需求详情 — 内容深度检查
   | 深度子项 | 状态 | 命中关键词 |
   | 页面原型与交互示意 | ✅ | 原型、figure |
   | 界面与展示规则(字段表/按钮权限) | ✅ | 字段名称、权限 |
   | 业务逻辑与边界条件(逐步操作逻辑) | ❌ 缺失 | — |
   | ... | ... | ... |

   待补充（已向你反问）：
   - 三、业务流程与架构·状态机：请补充订单/券的状态流转（起始状态+动作+条件=目标状态）
   - §四 逐步操作逻辑：请补充各功能的"前置条件→步骤→异常分支"
   - 七、关键边界设计检查清单：未找到逆向流/退款自检，请补充
   ```

7. **定稿门槛**：仅当所有必含板块均为 ✅（或用户明确豁免）时，方可判定“通过”并允许定稿/进入评审。

## 输出风格：简洁优先

本 skill 要求结构完整、字段细化、不确定性明确标注，但**不要求冗长**。写 PRD 时应遵循：

1. **能删则删**：删除与当前功能无关的背景铺垫、重复解释、过度修饰的过渡句。背景控制在 1-2 段，目标/指标用表格逐行呈现。
2. **用什么 + 条件/规则即可**：每个功能小节以「做什么」和「有什么条件/规则」为核心，避免大段叙事。逐步逻辑用编号步骤，异常分支用 bullet。
3. **表格承载细节**：字段映射、验收标准、边界条件、权限、埋点等尽量用表格，减少散文式描述。
4. **不确定项集中标注**：用「⚠️ 待确认 @干系人」一句话占位，不要展开解释为什么不确定。
5. **禁止为凑篇幅而扩写**：结构板块只能多不能少，但每个板块内部内容应精简到可开发/可评审所需的最小信息量。
6. **纯后端/接口契约 PRD 的例外**：若 PRD 明确不涉及前端界面（如仅定义后端接口、数据交互规则、Webhook 回调），可在 §四 中用一个简短「范围声明」列出不适用的前端深度子项（如界面设计/原型截图、交互说明、前端字段明细表、功能按钮权限表），并注明由哪份既有需求覆盖。结构排查时这些关键词会被命中，视为已声明。

## 关键边界（来自规范宗旨）

- 宁多勿漏：宁可多写，不可漏板块。
- 多端联动：涉及用户/运营/商家须全链路闭环，警惕“断头需求”。
- 凡变必录：变更须有版本记录并高亮 @ 干系人。

## §四 细节书写标准（强制套用团队《PRD 输出规范 260715》docx 模板）

> **权威模板来源**：团队《产品需求文档（PRD）输出规范与标准示例（修订于260715）》docx（"本规范文档同时作为部门内 AI 辅助生成 PRD 的 Standard Prompt 结构"）。
> 写 PRD 的 **§四 功能需求详情** 时，必须严格按该 docx 的「三、功能需求详情」+「商城小程序优惠券示例」每页骨架拆解，**禁止写一段扁平摘要**。
> 范本文件：`references/prd-detail-template.md`（已按 docx 重写）；写作骨架：`references/prd-authoring-skeleton.md`（写 PRD 前先铺空壳）。

### 写作流程（确保每次严格按格式输出 · 三重保障）
1. **先铺骨架**：复制 `references/prd-authoring-skeleton.md` 到新 PRD，把一~九板块 + §四 每页 2.1~2.7 子节空壳原样铺好，**先有结构再填内容**。
2. **逐页填 docx 结构**：每个本期新增/改动页面必须齐备：
   - **2.1 页面原型与交互示意**：贴 `<img>` 原型截图（禁流程 SVG 充数）；
   - **2.2 详细逻辑规则**：分「界面与展示规则（入参校验 / 极限值处理）」+「业务逻辑与边界条件（未登录拦截 / 交互反馈 / 按钮状态切换 / 防刷控制）」；
   - **2.3 列表字段表**（字段名称/需求说明/备注 + 排序/分页/合计/唯一性）；
   - **2.4 功能按钮总表 + 每个按钮独立小节**（功能说明/显示位置/权限/前置条件/功能实现=逐步+异常+校验文案）；
   - **2.5 编辑/新增表单**（区域/字段/输入限制/计算公式）；
   - **2.6 查询条件**；
   - **2.7 数据来源字段级**（取《XX表》/调XX接口）。
3. **写完跑阻断校验**：`python scripts/check_prd.py <prd.html> --strict`。
   - `--strict` 模式对「本期新增/改动页面缺 2.1 原型截图 / 2.2 详细逻辑规则」直接判 **🔴 不通过（阻断）**，不补不可定稿；
   - 非 strict 仅提醒。阶段2 深度扫描（DEPTH_ITEMS）+ §4.23/§4.24 偷懒/截图对齐扫描叠加兜底。

> **已有-沿用（tag r）功能点**：只写一句「沿用现有功能。」，不展开任何子节（§4.18）。
> **不确定性**：凡遇不确定数据，二选一——①「⚠️ 待确认 @干系人」占位；② 反问用户后据实书写。禁止臆测。

## 不确定性处理与反问机制（核心红线，不可跳过）

写 §四（以及任何板块）遇到不确定数据时，**第一反应不是编，而是问或标**。

**写之前**：先逐页面/逐功能点梳理「已知 vs 未知」，列出所有不确定点。凡属以下任一，即视为「不确定数据」，禁止臆测：
- 字段长度 / 输入限制 / 格式未指定；
- 按钮权限角色 / 数据范围未定义；
- 计算公式 / 分摊 / 状态流转未明确；
- 字段来源（前端 / 后端 / 第三方）不清楚；
- 异常提示文案、边界值未给；
- 任何「我觉得应该是…」「先这样占位」的假设。

**处理方式（二选一或并用）**：
1. **文档内占位**：以「⚠️ 待确认 @干系人」明确标注（模仿模板「具体逻辑需 @Lven 确认」），绝不编造内容填进去；
2. **主动反问**：用 `AskUserQuestion` 反问**具体、可落地**的问题（例：「XX 字段的输入长度限制是多少？」「未确认状态点击删除的提示文案是什么？」），拿到确切答案后再写。

**写之后**：必须向用户汇总「本次有 N 处待确认项，已标注/已提问」，不可静默带过。
若用户坚持先占位：只允许「⚠️ 待确认 @干系人」占位，**禁止编数值**。
阶段3 扫描（见脚本）会检测全文「待确认 / 需确认 / @X确认 / TBD / 待补充」等标记并列出，提醒澄清或保留占位。

## 阶段4：红线与图文一致性扫描（自动检查项，沉淀自评审踩坑）

本阶段目的是**从源头挡住「直播挂车」需求评审中暴露的四类问题**：图文臆造、范围外内容误入、埋点不规范、待确认悬空。脚本在阶段3 之后自动执行，输出四类告警。

### 4.1 红线词扫描（RED_LINE）
- **词库**：商家端后台 / 商家端 / 回放 / 火山SaaS / 火山 SaaS / SaaS配置 / 火山引擎直播配置 等（用户已裁定不纳入本项目的端口/能力）。
- **判定**：红线词出现时，若前后 30 字内**无**「不涉及 / 不在范围 / 排除 / 不配置 / 不开放」等豁免声明 → 告警。
- **处理**：若确为范围外，必须在文中明确写「本需求不涉及XX」；禁止把红线词当作功能实现描述写进 PRD。

### 4.2 待确认溯源（UNCERTAIN_TRACEABILITY）
- **判定**：提取每个「⚠️ 待确认 @干系人：<事项>」中引号「」/"" 内的字段名，若该字段**全文仅出现 1 次**（即只在待确认处、正文未定义）→ 告警"疑似悬空"。
- **根因**：本次「选品弹窗运营类型/品牌分类」待确认引用的字段正文根本不存在，属"先脑补字段再脑补待确认"。
- **处理**：删掉悬空待确认；或先在被引用处（如字段表）定义该字段再保留待确认。

### 4.3 埋点规范（TRACKING_V2_3）
- **判定**：PRD 含埋点内容时，若已链接引用《泰小虎埋点表v2.3》独立文档/在线规范 → 通过；否则须为 v2.3 双表（命中核心列≥12）→ 通过；若仅为 5 列简化版（所属终端/所在页面/事件名称/触发时机/上报参数）→ 告警。
- **处理**：改为 v2.3 双表，或拆成独立 HTML 后在 PRD 用链接引用（推荐，避免文档臃肿）。

### 4.4 图文一致性（DIAGRAM_CONSISTENCY）
- **判定**：检出「流程图/范围图/状态机/架构图」等图说关键词后，输出一份**人工核对清单**（图内文字不可直接解析）。
- **清单要点**（即本次踩坑项）：
  1. 流程图节点须与正文主流程逐条对应，不含正文未定义的功能（如仅"同步"却画"创建直播间"）；
  2. 影响范围图依赖系统须与正文"数据层/第三方依赖"逐条对应，不含正文未列出的依赖（如"用户账号/画像""商城订单""优惠券模块"）；
  3. 状态枚举须对接真实接口文档枚举值，禁止假设（如"违规下播"若接口无此值则须删除）；
  4. 图中出现的字段/概念须在正文有定义。
- **红线提醒**：生成任何图（流程图/范围图/状态机）后，**必须回读图内文字与正文逐条比对**，禁止脑补节点。

### 4.5 业务流程图一致性（FLOW_DIAGRAM_CONSISTENCY）🔴
- **前置规则（写 PRD 前必须满足）**：
  1. **必须先有已梳理确认的业务流程图**才能开始写 PRD §三。推荐格式：**横向泳道全链路图**（按端口/角色分泳道，按阶段分列，如 制券→配置→发放→领券→核销）。
  2. 若尚未梳理流程图 → **必须先停止写 PRD**，先画出业务流程图经用户确认后，再基于该图画 PRD。
  3. **📌 流程图必须从需求梳理文件获取**（2026-07-28 固化）：PRD §三的业务流程图应直接引用/嵌入「需求梳理阶段」产出的权威流程图文件（如 `XX-需求梳理图集.html`），**禁止在 PRD 中独立重绘与梳理文件不一致的流程图**。
     - 正确做法：在 PRD 流程图章节顶部标注 `📎 权威来源：《XX-需求梳理图集.html》§X`，SVG 内容与梳理文件保持一致（可原样复制或截图嵌入）。
     - 如需修改流程图 → **必须先修改需求梳理文件中的原图 → 再同步更新到 PRD**，不可只在 PRD 里改而不同步回梳理文件。
     - loop 排查检测到 PRD 流程图与梳理文件不一致时 → 按 Auto-Fix 规则（§4.10）直接替换为梳理文件版本，不确认。
- **判定**（check_prd.py 自动扫描）：
  - 🔴 **必须修**：PRD 检测到 `<svg>` / `<img>` 流程图，但流程图附近（±600 字）无以下基线声明关键词：
    `已梳理` / `横向泳道` / `泳道图` / `与.*流程图一致` / `依据.*梳理` / `本图与`
  - 🔴 **必须修**：PRD 有「业务流程图」章节标题但无任何图形内容
  - 🟡 **建议查**：图中提取的节点词对正文功能模块覆盖率 < 50%
- **修正方式**：
  - 若已有已梳理的泳道流程图 → 在 PRD 流程图旁标注
    「本图与《XX业务流程图（横向泳道·制券→核销全链路）》一致，
    节点/阶段/泳道一一对应」；
  - 若无已梳理图 → **撤回 PRD 流程图**，先补画横向泳道全链路图经确认后再重画。
- **踩坑背景**：优惠券需求 PRD 的 3.2 流程图为简化线性图（7 节点），
  与已梳理的横向泳道全链路图（4 泳道 × 5 阶段 × 15+ 节点）严重偏离——
  缺少制券模板库、发券引擎、券服务后台、火山引擎 API、数据看板等关键环节，
  且未按端口分泳道。

### 4.6 状态机完整性（STATE_MACHINE）🔴
- **判定**（check_prd.py 自动扫描，检出「状态机/状态流转」关键词后激活）：
  - 🔴 **必须修**：
    1) **宽泛起始状态**：状态转换表含「任意→删除」「任意→下架」等 → 缺状态守卫。
       每个破坏性操作须限定合法起始状态（如仅「下架」可「删除」，「启用」须先「下架」）。
    2) **破坏性操作前置条件过弱**：删除/作废/回滚的前置条件仅写
       「确认弹窗」「运营操作」→ 缺业务前置条件（无已发放券/无关联活动/先下架）。
    3) **循环/同态转换**：`启用→下架 目标=下架` 或 `A→操作→A` → 可能写反。
    4) **原型操作列缺按钮**：原型列表有「删除」但无「下架/启用/编辑」等状态变更按钮
       → 原型与状态机不对应，用户无法在 UI 上执行中间状态转换。
  - 🟡 **建议修**：
    5) 有转换表但未定义「完整状态枚举」（所有可能状态值的集合）。
    6) 子实体（发券活动/领券活动/用户券）的状态机仅为简短文字描述（<80字），
       未扩展为表格格式。
- **写 PRD 时必须逐条确认**（check 前 self-check 清单）：
  1. ✅ 原型列表操作列是否包含状态机定义的所有状态变更操作？
     （特别是下架/启用/停用/发布/撤回——不能只有查看+删除）
  2. ✅ 每个破坏性操作（删除/作废/回滚）是否有**业务级前置条件**？
     （不是仅"确认弹窗"，而是如"必须先下架"+"无已发放券"+"无进行中活动"）
  3. ✅ 状态枚举是否完整列出？边界状态（草稿/过期/锁定期）是否覆盖？
  4. ✅ 原型中每个操作按钮是否有关联的逐步逻辑？（含异常分支+校验提示文案）
- **踩坑背景**：优惠券 PRD 3.4 状态机表存在：
  - 「新建(默认启用)→下架→运营操作→下架」循环/同态；
  - 「任意→删除→确认弹窗→已删除」无业务守卫；
  - 原型操作列仅有「查看+删除」，缺「下架/启用/编辑」按钮；
  - 删除逻辑 `confirm→filter→toast` 无任何前置校验。

### 4.7 功能范围标注：已有 vs 新增/改动（SCOPE_TAGGING）🔴
- **规则（写 PRD §四 时强制）**：
  1. **比对需求梳理的范围**：动笔前先确认本期涉及的端口/功能，哪些在既往版本中<b>已存在</b>、哪些是<b>本期新增/改动</b>。
  2. 每个功能点（页面/模块/子功能）必须标注其一：
     - <span class="tag r">已有-沿用</span>：既往已存在的功能 → **仅写一句「沿用现有功能，详见原型 XXX.html」**，**禁止展开字段表/按钮表/逐步逻辑**（业务逻辑闭环在原型，PRD 不赘述）。
     - <span class="tag y">本期新增</span> / <span class="tag g">本期改动</span>：才逐功能点详写（字段表/按钮逻辑/表单/查询/数据来源）。
  3. **平台端与商家端是独立后台**：各自的新增/编辑/下架/删除是各系统原生功能，UI 无需对比统一或刻意区分。
  4. **删除/下架等破坏性操作若是已有功能**，同样仅标「沿用现有功能」，不重复展开细节；仅当本期对其有新增规则（如违规下架弹窗必填原因）才在对应行补述。
- **判定**（check_prd.py 自动扫描，检出「四、功能需求」章节后激活）：
  - 🔴 **必须修**：§四 下某个功能点（h3/h4 标题）**无任何范围标注**（无「已有/沿用/新增/改动/沿用现有功能」等关键词）→ 须补标。
  - 🟡 **建议查**：某功能点写了「沿用现有功能」却仍展开了大段字段表/逻辑 → 冗余，应压缩为一句。
- **踩坑背景**：优惠券 PRD 初版把平台端「新增/编辑/下架/删除」的字段表、按钮权限表、表单字段全量展开，
  但这些都是 gruul-mall 优惠券 addon 的<b>已有功能</b>（平台端原生能力），
  用户在评审中明确要求「已有功能不要在 PRD 里赘述，PRD 只要说一句沿用现有功能就行，
  只写本期新增或改动的功能」。后据此重建规则：§四 每个功能点强制标 已有-沿用 / 本期新增 / 本期改动。

### 4.8 埋点必要性自检（TRACKING_NECESSITY）
写 PRD 埋点清单（§五 本期涉及事件）时，每个候选事件必须能回答"为什么必须客户端埋点"，否则不纳入：
- **不埋①**：纯页面/组件内交互（如 Tab 切换、折叠展开、滚动到底）且无业务分析价值 → 不埋；若确需看各 Tab 曝光分布，用页面曝光事件带"当前Tab"参数即可，不单独建切换事件。
- **不埋②**：结果类/汇总类数据（如核销结果、领取成功结果、支付结果）若后端业务表（核销流水、发放记录、订单表）已落库、可直接统计 → 不重复做客户端埋点，避免双源口径不一致。
- **需埋**：用户行为意图（点击领券/点击购买/弹窗曝光关闭/进入某页）、且后端无法直接还原的事件才埋。
- **踩坑**：优惠券需求初稿曾把 `my_coupons_tab_switch`（券包Tab切换）、`coupon_redeem_result`（用券核销结果）列入埋点清单，经评审裁定移除——前者无分析价值、后者后端核销流水表可直接统计。

### 4.9 待确认项卫生 + 状态机前后矛盾（PENDING_HYGIENE）🔴
写 PRD 时，**待确认项（⚠️ 待确认 @干系人）不是"把矛盾丢给评审"的容器**。以下两类必须写 PRD 阶段就地 resolve，不得作为待确认项甩出：
- **不得与「设计如此」决策冲突**：若正文已裁定某项为既定设计（如"无重新上架/启用路径，下架即终态""编辑不允许变相上架"），则**不得**再把它写成待确认项（典型反面："⚠️ 待确认：编辑能否变相上架已下架的券？"）。这类问题应直接写成设计说明，结尾标注"（非待确认）"。
- **不得与现有/沿用功能冲突**：已标「已有-沿用」的功能（如平台端券的新增/编辑/下架/删除），其行为是否允许/限制由既有实现决定，**不要**就既有功能的核心行为提"是否允许/可否"类待确认项；若确属本期新增/改动，必须标「本期新增」并写清规则，而非含糊待确认。
- **状态机不得前后矛盾**：同一状态机转换表中，某起始状态**既**在其它行声明"无编辑 / 编辑已替换 / 无编辑需求"，**又**保留该状态的「编辑」行 → 直接矛盾。终态若禁止变相上架，应**直接删除编辑行**，而非同时保留编辑行与"无编辑"声明。（优惠券 PRD v1.0.7 实测：已下架行既写"编辑替换为删除、无编辑需求"又写"已下架→编辑 原型已有"，即此类矛盾，已删除编辑行修复。）
- 扫描器 `scan_pending_hygiene()` 自动覆盖：① 状态机转换表同状态"无编辑声明 vs 编辑行"冲突、同(状态,动作)映射不同目标；② 待确认项含"变相上架/重新上架"类提问且非否定语境。

### 4.10 Loop 自动修复模式（Auto-Fix）

**核心规则：loop 排查发现的问题，能直接修的不要让用户确认，直接改。**

#### 适用范围（可自动修复，无需确认）

| 问题类型 | 判定标准 | 修复动作 |
|---|---|---|
| **待确认项残留** | 可基于已有裁定/合理推断直接决定（如"商家端是否开放看板"→原型未做+商家端不需全平台看板→裁定不开放） | 改为明确标注，同步清理 §四 warn 块 + §九 汇总 |
| **状态机宽泛起始状态误报** | 匹配到非状态机上下文的关键词（如"全部功能模块""全部会员""全部店铺"） | PRD 文案微调（换近义词）+ 检测器加上下文过滤 |
| **流程图覆盖度不足** | 缺少明确的客户端入口节点（如商品详情领券） | 补全 SVG 节点 + 更新 smoke 说明文字 |
| **表格中 ⚠️ 待确认** | 属于已有功能沿用/不开放类决策 | 改为 ✓ / — + 小字注释说明理由 |
| **前后矛盾** | 同一事实在 PRD 两处表述冲突（如"已下架无编辑" vs "已下架→编辑"） | 保留与设计意图一致的版本，删除矛盾版本 |

#### 不适用范围（必须人工确认）

| 问题类型 | 原因 |
|---|---|
| **业务决策类** | 需要干系人拍板的功能取舍（如"是否支持 XX 场景"）|
| **KPI 阈值 / SLA** | 需要运营/管理层确定的具体数值 |
| **API 接口契约** | 需要技术 Owner 定义的字段/鉴权逻辑 |
| **外部依赖确认** | 需要第三方系统配合的集成方案 |

#### 执行流程

1. 跑 `check_prd.py` 完整扫描
2. 逐条审查阶段4 输出：
   - 若属「适用范围」→ **直接改 PRD** + 在版本记录中注明 `auto-fix: {问题描述}`
   - 若属「不适用范围」→ 保留为待确认项 @干系人
3. 复跑 loop 确认告警数下降
4. 推送 GitHub Pages

> **踩坑记录**：优惠券 PRD v1.0.7→v1.0.8 一次性修复了 4 类 loop 问题（状态机误报/表格待确认/流程图覆盖度/检测器精度），全部基于本规则直接执行未打断用户确认。

### 4.11 表格 CSS 视觉错位检测（TABLE_VISUAL_MISALIGN）🔴🟡
- **问题本质**：HTML 结构正确（列数匹配）但 **CSS 渲染层错位**——`<td>` 内含 `<br>` + 长文字在 `width:100%` 表格中撑爆列宽，导致整表视觉错位。`scan_table_quality` 原仅检测结构层，**完全漏掉此类问题**。
- **新增 3 项检测**（`scan_table_quality` 阶段4 扩展）：
  1. 🟡 `<td>` 含 `<br>` + 长文字（>12 字）→ 撑列风险，建议缩短文案或加 CSS 控制
  2. 🔴 `<table>` 缺 `table-layout:fixed` **且** 存在长内容 td → **高错位风险**，必须加 `table-layout:fixed` + `word-break:break-all`
  3. 🟡 单个 `<td>` 纯文本超长（>40 字）→ 建议折行或精简
- **Auto-Fix 修复方式**（适用范围，直接改不确认）：
  1. 全局 CSS 加 `table-layout:fixed` + `th,td{word-break:break-all;overflow-wrap:break-word}`
  2. 缩短 td 内长注释文字（如「不开放（商家端仅管自身券，无需全平台看板）」→「不开放（商家端仅管自身券）」）
  3. 超长纯文本 td（>40 字）拆行或用小字 span 缩减
- **踩坑**：优惠券 PRD §3.1 范围映射表 HTML 列数 6=6 完全正确，loop 报「✅ 全部表格结构正常」，但截图明显错位——根因是 `table{width:100%}` 无 `table-layout:fixed`，td 内 `—<br><span>不开放（商家端仅管自身券，无需全平台看板）</span>` 把商家端后台列撑爆。

### 4.12 矩阵表必须用 SVG 绘制（MATRIX_TABLE_MUST_BE_SVG）🔴
- **问题本质**：PRD 中的**交叉矩阵表**（如「端口×模块」「状态×条件」「角色×权限」）单元格以 ✓/—/已有功能 等短标记为主。经验证：HTML `<table>` 在 **GitHub Pages / Jekyll** 渲染管道下会发生**列错位（所有数据列内容挤到一列）**，即使加 `<colgroup>` 显式列宽 + 改 `table-layout:auto` 也**无法根治**——属平台级渲染差异，CSS 调整无效。
- **判定规则**（`scan_table_quality` 第 11 项，`scan_matrix_table_must_be_svg`）：
  - 表格 **列数 ≥ 4** 且 **短标记单元格占比 ≥ 50%**（短标记 = 文本≤8字且含 ✓/—/●/已有功能 等符号）→ 🔴 矩阵表，必须用 SVG 重绘
  - **不误伤**：状态明细表 / 字段表（单元格以长文本为主，`—` 仅作空占位）→ 占比 < 50% → **不告警**，HTML `<table>` 渲染正常
- **修复方式**（Auto-Fix，直接改不确认）：
  1. **改用 `<svg>` 重绘矩阵表**（参照 PRD §3.2 流程图 SVG 方案）：每个单元格 = 独立定位的 `<rect>`（背景色区分 ✓绿/—灰/已有功能红）+ `<text>`（精确居中坐标），**任意环境渲染一致**，不受浏览器 table 引擎影响。
  2. SVG 布局模板：`viewBox="0 0 W H"`，列 x 坐标数组 + 行 y 坐标数组，先画单元格填充 rect → 表头背景 → 网格线 → 文字（标记居中 `<text text-anchor="middle">`，长文本左对齐 `<text text-anchor="start">`）。
- **踩坑**：
  - 优惠券 PRD V1.0.10 §3.1 范围映射表（6 列短标记）在 GitHub Pages 上**全部挤到一列**；V1.0.11 试过 `colgroup` + `table-layout:auto`，**用户验证仍错位**；V1.0.15 最终改为 SVG 重绘，彻底解决。
  - 原 §4.12（TABLE_COL_SQUEEZE，检测 colgroup 存在性）是**错误路线**——colgroup 存在也错位，已废弃，改为本规则（直接禁止矩阵表用 HTML `<table>`）。

### 4.13 流程图防篡改保护（FLOW_DIAGRAM_TAMPER_PROOF）🔴
- **核心规则**：PRD §三 业务流程图**必须原样引用/嵌入已确认的权威流程图文件**（如 `coupon-flow.html` / `需求梳理图集.html`），**禁止 AI 自行简化、重绘、修改、省略节点或泳道**。
- **权威来源声明要求**：
  1. 流程图章节顶部必须标注 `📎 权威来源：《XX文件名》（含线上链接）`
  2. 必须包含约束声明：「⚠️ 禁止在 PRD 中自行简化/重绘/修改流程图。如发现差异须报用户确认后才可修改——AI 无权擅自改动」
  3. 若权威源含多张图（泳道图+时序图A+B），PRD 必须**全部内嵌或全部链接**，不得只选一张简化版
- **检测规则**（`scan_flow_diagram_consistency` 新增第 5 项）：
  - 🔴 有 SVG 但无权威来源引用（coupon-flow / 需求梳理图集 / 横向泳道 / 全链路）→ 告警
  - 🔴 引用了 coupon-flow.html 但图中无泳道关键词（平台端后台/商家端后台/券服务/火山引擎/用户端）→ 疑似被简化，必须回退完整版
  - 🟡 有 SVG 但无「禁止自行修改」约束声明 → 建议添加
- **差异报告机制**：
  - 当 loop 排查发现 PRD 流程图与权威源不一致时，**必须**：
    1. 停止任何自动修复
    2. 向用户列出具体差异（哪些节点/泳道/时序图缺失或被简化）
    3. 等待用户确认后才能修改
    4. 用户确认后，同步更新权威源文件（若用户要求改的是权威源本身）
- **踩坑**：优惠券 PRD v1.0.10 的 §3.2 流程图为自绘的简化 6 阶段线性图（触达领券→卡包到账→适用浏览→下单抵扣→分享裂变→边界异常），丢失了 `coupon-flow.html` 中的：
  - ① 整体业务泳道图（6 泳道：平台端后台/商家端后台/券服务·后端/火山引擎/用户端，5 阶段 × 15+ 节点）
  - ② 时序图 A：直播时长发券（运营→平台端→券服务→火山引擎→用户端，10 步）
  - ③ 时序图 B：商详领券→下单核销→关单返还（13 步 + alt 分支）
  
  v1.0.11 已回退为完整嵌入 coupon-flow.html 三张原图。

### §4.14 REDUNDANT_META_BOXES — 冗余 Meta 框自动删除（v1.0.12→v1.0.13 扩展）

**问题**：PRD 中出现两类面向 AI/评审过程的 meta 噪声框，均应直接删除：

#### A) 已闭环警告框（v1.0.12）
`<div class="warn">⚠️ 原型与状态机差异清单（已确认方案，待原型修正）`，但框内全部是「✅ 已解决」「设计如此」「已确认方案」等已闭环内容。

**规则**：扫描 `class="warn"` 框 → 有已闭环标记 + 无未闭环标记 → 🔴 直接删除

#### B) Meta 说明框（v1.0.13 新增）
`<div class="note">📎 权威来源：本节流程图引自 coupon-flow.html… ⚠️ 禁止在 PRD 中自行简化/重绘/修改流程图。AI 无权擅自改动…`

这类「来源引用 + 禁止修改声明 + AI 操作约束」是写给 AI/评审看的元信息，不应出现在交付 PRD 中。

**规则**：扫描 `class="note"` / 蓝色背景说明框（`background:#f0f5ff`）→ 命中 ≥2 个 meta 关键词 → 🔴 直接删除

meta 关键词清单：
- `📎 权威来源` / `权威来源`

### §4.15 PROTOTYPE_LINK_NOT_IMAGE — 原型示意必须嵌入截图（v1.0.14）

**问题**：PRD §四 功能需求详情中，每个端/模块的「原型示意」使用了 `<a href="...html">文字链接</a>` 而非 `<img>` 截图图片——读者需要额外点击跳转才能看到原型，不符合 PRD 自包含原则。

**规则**：扫描所有「原型示意」位置（3 种格式）：
- `<p>原型示意：</p><a href=...>` → 🔴 链接
- `<p>原型示意：<a href=...>` → 🔴 内嵌链接
- `原型示意…<a href=…>` → 🔴 附近出现链接

若命中且同一上下文（±300 字符）内无 `<img>` 标签 → 判定 **🔴 原型示意应为截图**

**修复方式**：
1. 用 Edge headless 对原型 HTML 截图：`msedge.exe --headless --disable-gpu --screenshot=out.png --window-size=1280,3000 "file:///path/to/原型.html"`
2. 将 `<p>原型示意：<a href="xxx.html">xxx</a></p>` 替换为 `<p>原型示意：</p><img src="coupon-prd-assets/xxx.png" style="max-width:100%;max-height:800px;border:1px solid #e0e0e0;border-radius:8px;object-fit:contain;">`
3. 截图文件需与 PRD 同目录或子目录（如 `原型截图/`），并推送到 GitHub

**踩坑**：优惠券 PRD V1.0.13 的 4 处原型示意全部为链接形式（coupon-platform / coupon-merchant / coupon-app / coupon-mini-h5），V1.0.14 全部替换为 Edge headless 截图。

### §4.16 PROTOTYPE_IMAGE_INVALID — 原型截图必须文件存在+样式规范（v1.0.16）

**问题**：PRD「原型示意」已改为 `<img>` 标签（§4.15 已通过），但图片仍显示为破损图标——原因是：
1. **src 路径引用的文件在本地磁盘不存在**（截图放到了 `原型截图/` 目录但 HTML 写的是 `coupon-prd-assets/`）
2. **文件未推送到 GitHub** → 线上 GitHub Pages 同样 404
3. **`<img>` 缺少 style 或 alt 属性** → 即使文件存在，展示效果也不规范

**规则**：对每个「原型示意」中的 `<img>` 标签执行三道校验（全部通过才放行）：

| # | 校验项 | 严重度 | 检测逻辑 | 不通过时提示 |
|---|--------|--------|----------|-------------|
| ① | 文件存在性 | 🔴 | `os.path.isfile(os.path.join(PRD目录, src))` | "图片文件不存在，线上会 404" |
| ② | style 规范 | 🟡 | style 含 `max-width` + `border` | "缺少 max-width/border，建议补全" |
| ③ | alt 属性 | 🟡 | 标签含 `alt="..."` | "缺少 alt 属性，建议补充语义描述" |

**标准 img 标签模板**（必须包含）：
```html
<img src="coupon-prd-assets/xxx.png"
     style="max-width:100%;max-height:800px;border:1px solid #e0e0e0;border-radius:8px;object-fit:contain;"
     alt="xxx端原型">
```

**修复方式**：
1. 确认截图文件路径与 HTML 中 src 一致（用 `ls` 验证）
2. 截图文件必须 `git push` 到 GitHub 仓库（GitHub Pages 只能访问仓库内文件）
3. `<img>` 标签补全 style + alt

**踩坑**：优惠券 PRD V1.0.14~V1.0.15 的 4 张截图因路径不匹配（`原型截图/` vs `coupon-prd-assets/`）+ 未推送，导致线上持续显示破损图标直至 V1.0.16 修复。

### §4.17 PROTOTYPE_IMAGE_OVERSIZED — 原型截图像素尺寸不得过大（v1.0.17）

**问题**：PRD「原型示意」截图在页面中渲染后产生大量空白（一张图占大半屏），读者需要大量滚动才能看到后续内容。
- **根因**：Edge headless 截图时 `--window-size` 高度设为整页滚动值（如 1280×3000），导致 PNG 文件包含大量无效空白区域
- **实际数据**（优惠券 PRD V1.0.16）：platform 1280×3000px / merchant 1280×3000px / app 1280×2000px / mini-h5 1280×1200px

**规则**：读取 PNG 文件 IHDR chunk 获取实际像素尺寸，超过阈值即告警：

| 阈值 | 值 | 严重度 | 说明 |
|------|-----|--------|------|
| 高度上限 | **1200px** | 🔴 | 超过则渲染后产生大量空白 |
| 宽度上限 | **1920px** | 🟡 | 通常不影响但浪费空间 |

**标准 img 标签模板**（必须包含，与 §4.16 合并）：
```html
<img src="coupon-prd-assets/xxx.png"
     style="max-width:100%;max-height:800px;border:1px solid #e0e0e0;border-radius:8px;object-fit:contain;"
     alt="xxx端原型">
```

**修复方式（二选一）**：
1. **CSS 兜底**（立即生效）：给 `<img>` 加 `max-height:800px;object-fit:contain;` 约束渲染高度
2. **重新截图**（根治）：缩小 Edge headless 的 `--window-size` 高度参数（建议 ≤1200）

**踩坑**：优惠券 PRD 4 张截图全部超高，V1.0.17 统一加 `max-height:800px;object-fit:contain;` 修复；§4.16/§4.17 共用同一 regex（支持跨段落匹配 `原型示意：</p><p><img>`）。

### §4.18 REUSE_FUNCTION_VERBOSE — 「已有-沿用」功能点禁止冗余赘述（v1.0.19）

**问题**：标注 `<span class="tag r">已有-沿用</span>` 的功能点写了一堆废话——按钮列表、原型链接、「本期仅补充 XXX」等上下文说明，这些不是产品功能描述，严重干扰阅读。

**根因**：AI 写 PRD 时对「沿用」功能的理解偏差，把"告诉读者这个功能有哪些按钮"当成了"功能需求说明"。

**规则**：
- **「已有-沿用」功能点的 `<p>` 段落只允许写一句**：「沿用现有功能。」
- **禁止出现**：按钮枚举（"列表、查询、新建/查看/删除/下架按钮"）、原型链接（"详见原型 coupon-platform.html"）、上下文补充（"本期仅补充：已下架/未开始行操作列「删除」替换原「编辑」"）
- **判定标准**：去除「沿用现有功能。」后段落仍有 >10 字符有效内容 → 🔴

**修复方式**：整段替换为 `<p>沿用现有功能。</p>`

**踩坑**：优惠券 PRD V1.0.18 的 §4.1.1~4.1.3 三个「已有-沿用」功能点分别写了 50~80 字的废话（含原型链接+本期仅补充），V1.0.19 全部精简为标准一句。

### §4.19 PROTOTYPE_SCREEN_RATIO — 原型截图统一使用 PC 端尺寸（v1.0.23）

**问题**：PRD 中原型截图曾按终端类型区分尺寸（PC 1440×900 vs 移动端 390×844），导致：

**规则**：**所有原型截图统一使用 PC 端尺寸 `1440×900` 截图**，不再区分终端类型。移动端原型内容在 1440×900 画布内完整展示即可。

|---------|------------|---------|------|

**修复方式**：

```bash
msedge --headless --screenshot=output.png --window-size=1440,900 原型文件.html
```

**踩坑**：

### §4.23 DASHBOARD_DIMENSION_TABLES — 数据看板/多维度列表页必须按维度输出完整字段表+聚合算法 🔴

| 属性 | 值 |
|------|-----|
| **严重度** | 🔴 |
| **检测函数** | `scan_dashboard_dimension_tables()` |
| **触发条件** | §四中出现「数据看板」「统计」「报表」「分析」「看板」「Dashboard」等关键词，且页面含多 Tab 维度切换（按XX维度/按YY维度） |

**问题本质**：数据看板/统计页有多个维度 Tab（如按券维度 / 按发放活动 / 券明细记录），但 PRD 只写了：
1. 概览指标卡片（总核销量/核销金额等几个数字）
2. 一个维度的字段表（或完全没有）
3. 模糊的一句「聚合《用户券表》」作为数据来源

**缺失内容**（必须补全）：
- **每个维度 Tab 的独立列表字段表**：字段名称 / 聚合算法（计算公式，如 `COUNT(…WHERE…)` / `SUM(…)` / `A÷B×100%`） / 数据来源（取哪张表） / 排序与筛选支持
- **派生字段算法**：领取率、核销率等百分比字段的精确计算公式 + 除零处理
- **合计行规则**：哪些列求和、哪些列取均值、哪些列仅展示
- **全局筛选对各维度的影响说明**

**标准模板**（每个维度一张表）：

```
### X.X.X 按XX维度列表字段表
| 字段名称 | 聚合算法（计算公式） | 数据来源 | 排序/筛选支持 |
| 券名称   | 取《券模板表》name，按template_id分组 | 《券模板表》 | 文本模糊搜索 |
| 总发行量 | SUM(《券模板表》total_stock)          | 《券模板表》 | 数值区间；默认降序 |
| 已领取   | COUNT(《用户券表》WHERE template_id=当前券) | 《用户券表》 | 数值区间 |
| 领取率   | 已领取÷总发行量×100%（保留1位小数）；总发行量=0时显示"—" | 派生 | 仅展示 |
| 核销量   | COUNT(《用户券表》WHERE template_id=当前券 AND status='已使用') | 《用户券表》 | 数值区间 |
| ...      | ...                                    | ...       | ... |
```

**判定规则**：
- 🔴 **必须修**：有「数据看板/统计页」但缺 ≥1 个维度 Tab 的完整字段表（含聚合算法列）
- 🔴 **必须修**：字段表存在但「聚合算法」列为空或仅写「取《XX表》」（无 COUNT/SUM/GROUP BY 等聚合函数）
- 🟡 **建议查**：有派生字段（率/比/均值）但未写除零/边界处理

**修复方式**：对照原型截图中的实际列头，逐字段补充聚合算法。若原型截图不可用，向用户确认各维度表格的完整列清单后再写。

**踩坑**：优惠券 PRD V1.0.24 的 P4 数据看板仅有 4 行概览指标 + 1 张券明细记录字段表，「按券维度」和「按发放活动维度」两个主列表完全没写——截图明确显示 9~10 列（券名称/类型/总发行量/已领取/领取率/核销量/核销率/核销金额/来源时间），PRD 却只写了一句「发放量/核销量/金额 聚合《用户券表》」。V1.0.25 补全两个维度的完整字段表（9 字段+10 字段，每字段均含聚合算法+数据来源+排序筛选）。

### §4.24 REQUIREMENT_MD_TAG_MISMATCH — PRD tag 与业务梳理 MD 状态矛盾（v1.0.24）

| 属性 | 值 |
|------|-----|
| **严重度** | 🔴 |
| **检测函数** | `scan_requirement_md_tag_mismatch()` |
| **触发条件** | PRD 中功能点标「已有-沿用」，但同目录业务梳理 MD 明确标注该功能为「暂无/需新增/仅xx有」 |
| **典型表现** | 平台端 D2 新建优惠券标「已有-沿用」→ 但 MD 写「平台端 \| 制券 \| 添加券 \| 暂无，仅商家端有」 |
| **处理方式** | 改为 `本期新增` + 按原型补详细 FR |

**数据源**：同目录下含 `需求梳理` / `线下定稿` / `范围确认` / `功能生命周期` 关键词的 `.md` 文件。

**解析逻辑**：
1. 读 MD 文件 → 解析 Markdown 表格行 → 提取 `(端口, 功能名, 状态)` 三元组
2. 判定"应为新增"的状态关键词：含 `暂无` / `需新增` / `仅xx有`
3. 提取 PRD §四 h4 标题关键词（去编号/括号/符号）
4. 与 MD 功能名做模糊匹配（重叠关键词 ≥2 即命中）
5. MD 说"需新增"但 PRD 标"已有-沿用" → 🔴 报矛盾

**匹配示例**：
| PRD h4 标题 | MD 功能名 | 重叠关键词 | 匹配？ |
|------------|----------|-----------|-------|
| D2 新建优惠券 | 添加券 | 新建≈添加, 券=券 (≥2) | ✅ 命中 |
| D1 券详情 | 编辑券 | — (仅"券") | ❌ 未命中（需人工确认） |
| P3 发放活动列表 | 创建发券活动 | 发放, 活动 (≥2) | ✅ 命中 |

**局限性**：关键词匹配非完美——名称差异大时可能漏报或误报。MD 无表格或格式不标准时不生效。**最终判定以人工核对为准**，本检测是辅助筛查。

**踩坑**：优惠券 PRD V1.0.17~V1.0.23 将平台端 4.1.2 D1 券详情和 4.1.3 D2 新建优惠券均标为「已有-沿用」（只写一句"沿用现有功能"），但业务梳理 MD 明确写平台端「添加券=暂无仅商家端有」「编辑券=暂无」。V1.0.24 修正为本期新增并补详细 FR。

### §4.25 MISSING_PROTOTYPE_FOR_NEW_FEATURE — 新增/改动功能缺少原型截图（v1.0.25，v1.0.28 增强优先级区分）

**问题**：PRD 中 4.1.2 D1 券详情、4.1.3 D2 新建/编辑券等标为 `本期新增` 的功能点，h4 小节内没有 `<img>` 原型截图标签。评审时用户明确指出"没有贴原型图"。

**根因**：
1. §4.15~§4.16 只检查 `<img>` 标签的**存在性和有效性**，不检查**每个新增功能点是否都有对应的截图**
2. **tag 升级后资源未同步**：V1.0.24 将 4.1.2/4.1.3 从 `已有-沿用` 改为 `本期新增` 时只补了 FR 文字，忘记补 `<img>` 截图
3. 告警无优先级区分：后台独立页面缺图与客户端子功能引用父级图混为同一严重度

**规则（v1.0.28 增强）**：

| 检查项 | 判定逻辑 | 严重度 | 说明 |
|--------|---------|--------|------|
| 后台独立页面缺图 | h4 tag 含「本期新增」→ 标题含「详情/新建/编辑/列表/看板/查询/管理」或所在 h3 为平台端/商家端 → h4 内无 `<img>` | 🚨 阻断 | 必须补独立截图才能定版 |
| 客户端子功能无独立图 | h4 tag 含「本期新增」→ h4 内无 `<img>` 但所在 h3 顶部有总览图或文中引用了原型 | 🟡 提醒 | 建议补图，可忽略 |
| 豁免 | 标题含「差异说明」「状态机」「流程」「说明」「附录」等非页面类关键词 | 跳过 | — |

**修复方式**：
1. 从对应端口原型 HTML 中定位目标页面（通过 id 或 nav）
2. 创建临时快照页（修改默认显示视图），用 Edge headless 截取 1440×900
3. 以 `<img src="coupon-prd-assets/xxx.png" style="max-width:100%;max-height:800px;...">` 插入到该 h4 小节内
4. 列表页和表单页各一张

**踩坑**：优惠券 PRD V1.0.24 将 4.1.2(D1)/4.1.3(D2) tag 改为「本期新增」后未同步补截图，V1.0.28 评审发现时已隔 4 个版本。此后任何 tag 升级操作必须同步检查截图资源。

### §4.28 TAG_UPGRADE_IMAGE_SYNC — tag 升级必须同步截图资源（v1.0.28 新增）

**问题**：PRD 功能点 tag 从 `已有-沿用`(r) 升级为 `本期新增`(y) 或 `本期改动` 时，仅补充 FR 文字内容（字段表/按钮表/操作逻辑），**遗漏同步补 `<img>` 原型截图**。

**根因**：tag 升级操作通常是局部修改（改 span class），修改者注意力集中在文字内容上，忽略了"新增/改动功能需要原型佐证"这一隐式规范。

**规则**：

| 场景 | 检测方式 | 要求 |
|------|---------|------|
| tag r→y 升级 | §4.25 共享检测逻辑（blocker/warn 分级） | 除 FR 外必须同步补 `<img>` |
| tag r→y + 有字段表/表单字段但无图 | §4.25 阻断级判定（含表单类关键词） | **强制阻断**，不补图不可定版 |
| 已有-沿用保持不变 | 不触发 | 无需截图 |

**与 §4.25 的关系**：§4.28 不是独立检测函数，而是 §4.25 增强版的**命名别名和语义标注**。当 §4.25 报出🚨阻断级告警且该功能点在业务梳理 MD 中原为"已有"时，同时触发 §4.28（tag 升级后资源未同步）。

### §4.26 MIXED_VIEW_SCREENSHOT — 多视图必须分图截取（v1.0.26）

**问题**：PRD 中一个 h4 功能点包含多个视图（如「P2 发券活动列表 + D3 新建表单」），但只放了 **1 张截图**把多个视图混在一起。读者无法分辨每个页面的具体样式。

**根因**：截取原型时贪方便，把列表页和表单页/详情页/弹窗等一次性截在一张图里；或未意识到一个功能点可能对应多个独立页面。

**规则**：

| 场景 | 要求 | 示例 |
|------|------|------|
| h4 标题含「+」「／」等多视图分隔符 | 每个视图独立一张 `<img>` | 「P2 列表 + D3 新建」→ 2 张图 |
| 节内有 `<p><b>列表</b>` + `<p><b>新建表单</b>` 等多个子视图标题 | 每个子视图标题后跟独立 `<img>` | 列表 1 张 + 新建表单 1 张 |
| 弹窗/抽屉/Drawer | 单独截图，不与父页面混在一起 | 「获券弹窗」单独 1 张 |
| 详情页 | 单独截图，不与列表混在一起 | 「券详情」单独 1 张 |

**判定方式**（`scan_mixed_view_screenshot`）：
1. 遍历所有 tag 为「本期新增/改动」的 h4
2. 标题含 `+`/`／`/`、` 但该节 `<img>` 数 < 2 → 🔴
3. 节内 ≥2 个视图类 `<p><b>` 子标题但 `<img>` 数 < 子标题数 → 🔴

**修复方式**：按视图分别截取独立图片：
```bash
# P2 列表页
msedge --headless --screenshot=p2-list.png --window-size=1440,900 p2-list-view.html
# D3 新建表单页
msedge --headless --screenshot=d3-form.png --window-size=1440,900 d3-form-view.html
```

**踩坑**：优惠券 PRD V1.0.25 的 4.1.4 只放了一张 `coupon-d3-send-edit.png`，上半部分是 P2 列表、下半部分是 D3 新建表单——两个视图混在一起。V1.0.26 拆为 `coupon-p2-send-list.png`（纯列表）+ `coupon-d3-send-edit.png`（纯表单）两张独立截图。

### §4.27 VERBOSE_TABLE_ANNOTATIONS — 表格中的冗余验证备注须删除（v1.0.27）

**问题**：PRD 表格（尤其是状态流转表）的单元格里混入了开发/设计阶段的调试备注，以绿色小字 ✅ 形式出现，如：
- `✅ 原型已有（截图验证：进行中行显示红色"下架"）`
- `✅ 方案确认：已下架/未开始行的操作列将原下架/编辑替换为「删除」`
- `✅ 原型已验证（截图确认：平台端弹窗含必填原因输入框）`
- `✅ 同上`

**根因**：写 PRD 时边对照原型边加的自我验证笔记，忘记在定稿前清理。

**规则**：

| 冗余模式 | 特征 | 处理 |
|---------|------|------|
| 绿色 ✅ span 备注 | `<span style="color:#2ba245;font-size:11px">✅ ...</span>` | 🔴 直接删除 |
| 括号内验证备注 | `（复数验证：...）` / `（截图验证：...）` / `（方案确认：...）` | 🟡 确认后删除或改写为正式表述 |
| 「同上」懒引用 | `✅ 方案确认：同上` | 🔴 删除或展开为完整说明 |

**判定方式**（`scan_verbose_table_annotations`）：
1. 正则匹配 `<span style="color:#2ba245;font-size:11px">✅ ...</span>` → 🔴
2. 在 `<td>` / `<th>` 内搜索括号类验证备注 → 🟡

**修复方式**：直接删除整段 `<span>` 标签及其内容；如该单元格无其他内容则保留按钮/位置描述本身。

**踩坑**：优惠券 PRD V1.0.26 的「优惠券配置状态转换表」原型按钮位置列，5 行均带绿色 ✅ 冗余备注。V1.0.27 全部清除。

### §4.29 MODAL_POPUP_MISSING_SCREENSHOT — 弹窗/弹框类功能点必须独立截图（v1.0.29）

**问题**：PRD 中 4.3.2「获券弹窗（系统发券触达）」标为 `本期新增`，标题明确含「弹窗」关键词，但 h4 小节内无 `<img>` 独立截图——仅引用了父级页面（App 首页）的总览图。评审时用户指出"这个明明是弹窗你只有页面原型"。

**根因**：§4.25（MISSING_PROTOTYPE_FOR_NEW_FEATURE）检测的是"新增/改动功能缺图"，但不区分**页面级截图**和**组件级截图（弹窗/弹框）**。弹窗是覆盖在页面之上的独立 UI 组件，其内部布局（标题区 / 内容列表 / 操作按钮 / 关闭方式）无法从父级页面总览图中看到。当前 skill 没有对"标题含弹窗关键词的功能点必须截取弹窗状态截图"做专项检测。

**规则**：

| 检查项 | 判定逻辑 | 严重度 |
|--------|---------|--------|
| 弹窗类功能点缺独立截图 | h4 标题含「弹窗」「弹框」「Modal」「Popup」「对话框」「抽屉」「overlay」「dialog」→ 该 h4 到下一 h4 之间无 `<img>` | 🔴 |
| 排除（非组件，不要求独立截图） | 标题同时含「差异」「对比」「规范」「外壳」「diff」「入口」「示意」「总览」「引用」「说明」→ 视为引用/差异说明，跳过 | 跳过 |

**与 §4.25 的关系**：§4.25 检测"新增/改动是否缺图"，§4.29 检测"弹窗类组件是否有独立截图"。两者互补——一个功能点可能同时触发两条规则（如 4.3.2 获券弹窗），也可能只触发 §4.29（如果该弹窗功能被标为"已有-沿用"但实际缺少弹窗截图）。

**修复方式**：
1. 从对应端口原型中定位弹窗触发入口
2. 创建临时快照页，强制弹窗显示（修改 class 或加 setTimeout 触发）
3. 用 Edge headless 截取 1440×900（弹窗完整展示）
4. 以 `<img>` 标签插入到该 h4 小节的 4.x.x.1 原型与交互示意处

**踩坑**：优惠券 PRD V1.0.28 的 4.3.2 获券弹窗一直引用 App 首页总览图替代弹窗截图，直到 V1.0.29 才补上独立弹窗截图。V1.0.30 优化：4.3.1「首页·获券弹窗入口」（含"入口"）与 4.4.1「外壳差异」（含"差异/外壳"）曾误报为缺弹窗截图，已通过排除关键词消除——它们分别是"入口卡（被首页总览图覆盖）"和"端差异对比表（非组件）"，不应要求独立弹窗截图。

### §4.30 SCREENSHOT_DUPLICATE_DETECTION — 截图内容不可互相重复（v1.0.30）

**问题**：优惠券 PRD 转 Word 时，发现 14 张截图实际只嵌入了 12 张。根因是 `coupon-app.png`、`coupon-app-arrival-modal.png`、`coupon-app-my-coupons.png` 三张 **md5 完全相同**——之前截取 my-coupons / arrival-modal 时原型视图未正确切换（截到了首页默认视图），但图片"存在"且路径正确，常规存在性检测（`§4.25`/`§4.29`）发现不了。Word/钉钉等容器对相同字节的图片会**去重为 1 张**，导致其余视图"看起来有图、实际缺失"。

**规则**：

| 检查项 | 判定逻辑 | 严重度 |
|--------|---------|--------|
| 多张截图内容相同 | 提取所有 `<img src>` 对应的本地 PNG，按 md5 分组，组内 ≥2 张 | 🔴 |

**与 §4.25/§4.29 的区别**：§4.25/§4.29 查"图是否存在"，§4.30 查"图是否内容独立"。即使每张图都存在且路径正确，若内容互相重复仍会导入后缺图。

**修复方式**：
1. 重新从原型截取重复的视图，确认页面已正确切换（`go('p_xxx')` 同步调用）或弹窗已触发（`showArrival()` 等）再截图
2. 截图后用 `md5sum` 比对，确保与首页/其它图不同
3. Edge headless 截取动态视图时，**不要在快照 HTML 里只改 class**（JS 初始化会重置），应在 `</body>` 前注入同步调用 `<script>go('p_c2');</script>`，并加 `--virtual-time-budget=2500` 保证 JS 执行完

**踩坑**：优惠券 PRD V1.0.30 转 Word 前，arrival-modal 与 my-coupons 两张图 md5 与首页图一致（均为 `d0aeebb8…`），重截后 md5 变为 `39e0a0a7…` / `73f1542d…`，Word 才嵌入完整 14 张。

### §4.31 SCREENSHOT_VIEW_MISMATCH — 截图内容必须匹配功能点视图（v1.0.32）

**问题**：优惠券 PRD 4.3.4「商品详情领券」有 `<img>` 截图、路径正确、md5 也唯一（通过 §4.30 去重检测），但截图实际显示的是 **App 首页菜单导航视图**（M1~M5 列表），不是商品详情页（p_c5）。用户评审时一眼看出「这是首页不是商品详情」。根因是 Edge headless 截图时原型视图未切换到位——注入的 `go('p_c5')` 因时序问题未执行，或根本没注入切换脚本，截到了默认首页。

**与 §4.30 的区别**：
- §4.30 查「多张图内容是否重复」（md5 相同 → 去重丢图）
- §4.31 查「单张图内容是否对」（md5 唯一但显示的是错误视图 → 即使不丢图也是错的）
- §4.30 能抓出「截了两次首页」；§4.31 能抓出「只截了一次首页但贴在了商品详情下面」

**规则**：

| 检查项 | 判定逻辑 | 严重度 |
|--------|---------|--------|
| 截图为原型默认/首页视图 | 有 `prototype_screenshot_map.json` 时：map 指定了 `view`（如 `p_c5`），但截图 md5 == 该原型的「首页基准 md5」→ 视图未切换 | 🔴 |
| 文件名与视图语义矛盾 | 文件名含 `detail/product/商品详情` 等关键词，但同原型其他截图（如 coupon-app.png 首页）视觉特征高度相似（文件大小偏差 <5% 且宽高相同） | 🟡 |
| auto-fill 后校验 | `--auto-fill` 截取后立即比对首页基准 md5，命中则自动重试（加大 setTimeout 延迟到 1500ms 并二次截图） | 🔴（auto-fix） |

**检测实现**（`check_prd.py` 新增 `scan_screenshot_view_mismatch()`）：

1. **首页基准采集**：首次运行时，对每个原型 HTML 用 Edge headless 截取**无注入**的默认视图，记录 md5 为 `{proto_file}_home_md5`（缓存到 `.screenshot_baseline.json`）
2. **逐图比对**：遍历 PRD 中所有 `<img src="coupon-prd-assets/*.png">`，读取本地 PNG 的 md5
3. **交叉验证**：如果某截图的 md5 == 任一原型的首页基准 md5 → 该截图实际是首页，标记为 🔴 视图不匹配
4. **map 校验**：如果有 `prototype_screenshot_map.json`，额外检查 map 中 `view` 字段非空的条目——其对应截图不应命中任何首页基准 md5

**修复方式**：
1. 确认该功能点应在原型中显示哪个视图（查看 map 的 `view` 字段或从 h4 标题推断）
2. 创建临时副本 HTML，在 `</body>` 前注入 `<script>setTimeout(function(){if(typeof go==='function')go('VIEW_ID')},800)</script>`
3. 用绝对路径 `--screenshot="ABSOLUTE_PATH"` 重截（相对路径可能写到 Edge 工作目录导致不覆盖）
4. 截完后验证 md5 ≠ 首页基准 md5
5. 推送新图替换 GitHub Pages 上的旧图

**踩坑**：优惠券 PRD V1.0.32 发现 4.3.4 商品详情领券截图（coupon-app-product-detail-coupon.png, 67KB）实际是 App 首页菜单视图。根因：之前 --auto-fill 补图时用的注入方式在部分 Edge headless 实例中时序不稳定。修复后用「原型副本追加 script + 绝对路径输出 + virtual-time-budget=3000」三重保障重截，新图 134KB/md5=`c6932864…`，确认显示 C5 商品详情页。

## §4.32 PROTOTYPE_PRD_SYNC — 改原型必须同步改 PRD（v1.0.33 · 强制联动）

**问题**：优惠券 PRD 评审时，第 1 点「双端列表页加总库存」只改了平台端/商家端原型（新增「总库存」列），没有同步改 PRD 的列表字段表。虽然后续第 2 点顺带补回了，但流程上「改原型不同步 PRD」是漏改隐患——原型与 PRD 会逐步失配，评审时难以察觉。

**规则（代理行为约束，非运行时检测）**：

| 场景 | 处理 |
|------|------|
| 修改任一原型文件（平台端后台原型.html / 商家端后台原型.html / App端原型.html / 小程序H5原型.html / 其他命名含「原型」的 HTML） | **必须**在本轮改动内同时修改对应 PRD 的相同章节 |
| 同需求目录下**存在** PRD（文件名含 `PRD` 或 `需求` 的 .html） | 同步改：列表字段表 / 表单字段表 / 按钮表 / 功能逻辑 等对应处，保证原型列名、按钮、字段与 PRD 一致 |
| 同需求目录下**不存在** PRD（本期不做需求文档 / 仅出原型） | **跳过**，但必须在回复中明确说明「本期无 PRD，原型改动未同步文档」并在该需求记忆/日志标注 |
| 用户显式说「先只改原型」「PRD 下轮再更」 | 允许跳过，但必须登记待办，下一轮 PRD 改动时优先补回 |

**同步核对清单（每次改原型后自问）**：

1. 原型列表 `<th>` 新增/改名/删除了列？→ PRD 的「列表字段表」首列同步增删改名
2. 原型按钮（onclick）新增/改名/改显示条件？→ PRD 的「功能按钮表」同步
3. 原型表单 `<input>`/字段改了？→ PRD 的「表单字段表」同步
4. 原型交互逻辑（展开/折叠/toast/弹窗）改了？→ PRD 的「功能逻辑/逐步操作」同步
5. 双端（平台端+商家端）都改了？→ 商家端若引用平台端章节（如 §4.2.2「同平台端 4.1」），确认引用仍然成立；若商家端有独立差异表，逐端核对

**检测实现**（`check_prd.py` 新增 `scan_prototype_prd_sync()`，启发式联动检测）：
- 遍历同目录所有「原型」HTML，提取每个 `<table>` 的 `<th>` 表头集合
- 提取 PRD 中所有「列表字段表 / 表单字段表」等表格的**首列**字段名集合
- 比对：原型 `<th>` 中出现、但 PRD 字段名集合**完全不存在**的列（排除纯 UI 列「操作」「状态」白名单）→ 判为 🟡「原型有此列但 PRD 未描述，疑似漏同步」
- 反向：PRD 字段名有、原型表头无 → 🟡「PRD 描述了但原型缺列，疑似原型漏做」
- 该函数为**启发式提醒**，可能误报（如列名表述不同），需人工确认；目的是在评审前兜底抓「改了一边忘另一边」

**踩坑**：优惠券 PRD V1.0.33 评审，第 1 点「双端列表加总库存」只改了原型忘改 PRD，直到第 2 点改 PRD §4.1.1 才顺带补回总库存行。此后固化本规则：改原型=改 PRD 必须成对出现。

### §4.33 PROTOTYPE_FUNCTION_COVERAGE — 原型功能必须完全写进 PRD（v1.0.34 · 用户强需求）

**问题**：用户评审后明确要求「prdskill 有没有检查原型功能是否完全写进去的检查，没有要有，然后固化到 skill 不要漏功能」。即：**原型里做的每一个业务功能（按钮/弹窗/表单/交互），PRD §四 都必须有对应描述**，漏写即告警。

**与 §4.32 的区别**：§4.32 只比对「表格列名」（`<th>`），属于数据层同步；§4.33 比对的才是**业务功能点**——按钮、onclick 处理函数、弹窗标题、表单字段标签等。两者互补：§4.32 防「列表加了列没写字段表」，§4.33 防「做了个按钮/弹窗/表单没写功能说明」。

**检测实现**（`check_prd.py` 新增 `scan_prototype_function_coverage()`，阶段5 输出）：

1. **定位原型文件**：`_collect_proto_files(base_dir)` 收集 PRD 同目录 + **父目录**内文件名含「原型」的 HTML（常见布局：PRD/xxx-PRD.html 与 父目录/xxx-原型.html 同需求分块）。
2. **提取原型「业务交互特征」**（刻意排除导航/Tab/侧边栏菜单——属应用框架 chrome，非本期业务功能）：
   - ① `<button>` 文本（如 下载明细 / 明细 / 确认赠送）
   - ② `onclick="函数名("` 处理函数（downloadDetail / tagSearch / submitBatch 等，配 `FUNC_SEMANTIC` 语义映射表判断 PRD 是否描述了该功能）
   - ③ 弹窗/面板标题（modal|dialog|popup|overlay|panel 容器内的 h2~h4，及 class 含 title|label 的短文本，如 标签筛选 / 目标用户列表）
   - ④ 表单字段 `<label>` 与 `placeholder` 输入提示
3. **降噪**：剔除含 emoji/箭头/几何图形/全角标点等符号的 token、纯 UI 动词白名单（确定/取消/搜索/重置…）、应用框架导航词（内容管理/用户体系/数据分析…）。
4. **覆盖比对**（多重容错匹配，降低术语表述差异误报）：
   - 直接命中 / 去中文后缀（列表/区/项…）/ 分隔符拆分（批量赠送/扣除 → 批量赠送）/ **滑动 2~3 字连续 CJK 子串**（批量赠送虎力值 → 批量赠送·虎力值）；
   - onclick 英文名按其语义映射关键词匹配；
   - 原型有、PRD §四 全无对应 → 🟡「原型功能 PRD 未描述（疑似漏写，§4.33 功能覆盖）」。

**判定口径**：
- 🟡（建议查，非阻断）：原型业务功能在 PRD §四 找不到描述。属「疑似漏写」提醒，需人工核对；确为纯 UI 动词或本期无对应需求的，可忽略并说明。
- 本检查**不阻断定稿**（与 §4.25 等阻断级不同），因为原型可能含超出本期 PRD 范围的演示性内容；其目的是在评审前兜底抓「做了一边忘另一边」。

**踩坑**：初版只扫 PRD 同目录，而本项目原型在父目录 → 静默跳过，等于没查。已改为同时搜父目录。另初版未排除导航 chrome，把原型整套 App 侧边栏（内容管理/用户体系…）和 emoji 视图切换按钮全报成漏写，噪声爆炸；已加符号过滤 + 导航白名单 + 滑动子串匹配三重降噪，实测 虎力值 PRD 由「20+ 误报」收敛为「0 误报且能抓住真实缺口」。

## 自动补图（V1.0.30 新增 · 检出即补，不询问）

**核心原则**：检测到缺图后**直接生成并插入截图**，不向用户确认。这是"不要出现很多图缺失"的根本保障——排查与修补在同一流程内闭环。

**用法**：在 `check_prd.py` 后加 `--auto-fill` 参数：

```bash
python check_prd.py <prd.html> --auto-fill
```

脚本会：① 运行 `find_missing_screenshot_sections()` 合并 §4.25+§4.29 判定找出所有缺图小节；② 读取 PRD 同目录的 `prototype_screenshot_map.json`；③ 对每个缺图小节按映射表从原型 HTML 强制显示目标视图 → Edge headless 截取 1440×900 → 以 `<img>` 插入该 h4 小节开头；④ 输出已补/失败/跳过清单。

**`prototype_screenshot_map.json` 结构**（放在 PRD 同目录）：

```json
{
  "<h4标题(去tag后的纯文本)>": [
    {"proto": "平台端后台原型.html", "view": "viewX",
     "out": "coupon-prd-assets/xxx.png", "label": "说明",
     "kind": "platform|app|modal(可选)", "trigger": "setTimeout(showX,200);(弹窗可选)"}
  ]
}
```

- `kind` 可省略（自动按 DOM 特征判定：含 `class="page active"` → app；否则 platform）。
- 一个 h4 可映射多个视图（如 4.1.5 P3+D4 拆成「列表」+「新建表单」两张图，满足 §4.26 不混图）。
- 已含 `<img>` 的小节不会重复补；mapping 未覆盖的缺图小节会报告「需人工补图」。

**判定对齐**（与 §4.25 报告逻辑一致，避免误判"被父级总览图覆盖"的子功能为缺图）：
- 后台端（平台/商家端）功能点无 own `<img>` → 必补
- 标题含独立页面关键词（详情/新建/编辑/列表/看板/查询/管理）无 own `<img>` → 必补
- 弹窗类（已排除 差异/规范/外壳/入口 等）无 own `<img>` → 必补
- 其余客户端子功能：若所在 h3 顶部已有父级总览图 → 视为已覆盖（如 4.3.1 首页入口卡），跳过；否则仍判缺图

**踩坑**：优惠券 PRD 曾一次性缺 7 张图（D1/D2/P3/P4/4.3.2/4.3.3/4.3.4），靠人工逐张发现。固化 `--auto-fill` + 映射表后，一次命令即可全部补齐，且后续每次写新 PRD 只要维护映射表就能自动补图。
