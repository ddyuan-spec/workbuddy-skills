# 需求确认门禁（requirement-confirm-gate）

> **唯一铁律**：拿到需求 → 先确认理解 → 有不确定就反问 → 确认后才动手产出。
> 禁止"拿到就做"、禁止用默认假设替用户拍板、禁止臆造数据/规则/口径。

## 何时强制触发
- 用户给评审意见 / 反馈，要据此改 PRD 或原型；
- 用户描述一段新需求，信息可能不全；
- 任何涉及"写/改/审 PRD、画/改原型、推线上"的任务开头。

## 执行步骤（强制顺序）
0. **需求拆透（BLOCKER 前置）**：确认理解前，凡是"写/改/审 PRD、画/改原型、评审"类新需求，**必须先调 `requirement-analysis` 跑完 6 步需求拆透**（还原真实问题→识别角色→拆场景→梳流程→异常边界扫描→模拟评审），产出结构化分析结论后才允许往下。轻量例外（纯排版/纯文案润色/已知明确的单点字段修改）可跳过本步只走下方反问。
   > 这是默认动作：拿到需求先拆透，再确认、再产出。详见 `requirement-analysis` SKILL.md。
1. **读懂现状**：先读相关现有文件（PRD / 原型 / 截图 / 后台字段），定位要改的板块，不要凭空写。
2. **复述需求**：用一两句话把用户意图复述回去，证明你理解了，而不是急着产出。
3. **列出不确定点**：逐条标出语义模糊、缺数据、缺口径的地方。典型不确定：
   - 数字 / 阈值（加多少分、窗口几天、权重几倍）未给；
   - 模块结构变化（合并 / 拆分 / 新增字段）意图不清；
   - "改为XX"类表述，不清楚是替换触发条件还是替换算法；
   - 作用范围（对哪些策略 / 用户态生效）未说明。
4. **反问确认**：用 AskUserQuestion 把不确定点抛给用户（≤4 题/轮，按"阻塞产出的 → 影响质量的"排序），每题给 2–4 个具体可选项 + Other 兜底。
   - 同时在 PRD 内用「⚠️ 待确认 @干系人」占位，绝不填臆测值。
5. **确认后再产出**：拿到回答后才动笔改 PRD / 画原型；改写时把确认结论落到具体字段 / 公式 / 结构上。
6. **汇总待确认项**：交付时附"本次仍待确认项清单"。

## 红线（违反即算失误）
- ❌ 用户一说"改 PRD / 重写"，立刻通篇重写而不反问模糊点。
- ❌ 把"改为下单""返回第一个和前两个"这类模糊表述，按自己猜的意思直接落地。
- ❌ 缺数据时编一个"合理值"填进去（必须占位 + 反问）。

## 与其他 skill 的关系
- 本门禁是**最前置**一步；其中步骤 0 固定先调 `requirement-analysis` 拆透，走完再路由到 prd-suite / proto-c / proto-admin / pm-review-board / delivery-suite。
- 与 requirement-workflow 的 intake 提问同源，本门禁更强调"不确定就反问、别臆造"的硬性约束。
